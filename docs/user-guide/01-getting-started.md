# 01 首次使用：把简历变成可执行的求职方向

[返回指南首页](README.md) · [下一章：找岗与岗位判断](02-job-discovery-and-matching.md)

第一次使用的目标不是填完一堆表，而是让系统准确理解三件事：**你做过什么、想找什么、这次去哪里找。**

## 1. 先完成外部连接

普通安装版从[正式发布页](https://github.com/daydreamer0213/OfferGo/releases/latest)获取安装器，安装后从桌面或开始菜单的 **OfferGo** 图标启动，具体步骤见[安装版说明](../installed-user-guide.md)。源码预览使用当次启动给出的地址；公开 v1.4.1 与本文当前源码的功能差别先看[第08章](08-status-and-documents.md)。工作台就绪后：

1. 进入 **招聘平台**，选择使用的平台，在专用 Edge 中完成登录并检查工作区。
2. 进入 **模型与设置**，填写自己的模型服务信息，点击 **测试连接并保存**。
3. 进入 **简历工作室**，上传或粘贴简历，开始建立资料。

平台连接负责“能不能读取岗位”，模型连接负责“能不能理解和生成内容”，简历资料负责“按谁的实际情况判断”。任何一个缺失，都不能由另外两个替代。

连接、资料位置及失败处理见 [07 设置、资料与恢复](07-settings-data-and-recovery.md)。

## 2. 为什么要分成四份资料

| 资料 | 它回答的问题 | 一个例子 |
| --- | --- | --- |
| 原简历 | 你原本写了什么，有哪些可追溯事实 | “负责检索接口与结果展示” |
| 候选人画像 | 系统怎样整理你的背景、经历与求职意向 | 本科；做过应用开发；希望在广州找工作 |
| 匹配偏好卡 | 哪些经历是直接证据，哪些能力可以迁移，哪里需要谨慎 | 接口开发有实际项目；做过检索，但没有据此证明底层模型训练能力 |
| 搜索方案 | 本轮按什么范围和搜索词寻找机会 | 广州、应用开发方向、按本人意愿设置薪资与经验范围 |

它们不是四份需要重复填写的简历。项目从已有简历提炼资料，让你检查关键判断。

分开保存的原因是：**事实、系统理解和求职选择会以不同方式变化。** 你换一个求职城市，不代表项目经历变了；你补充一次真实工作，也不代表应该自动改变所有搜索条件。

## 3. 上传简历后，系统实际做什么

### 第一步：提取可读文本

支持 TXT、Markdown、DOCX 和 PDF，也可直接粘贴文字。文档先转成可分析文本，再进入简历理解。

简历理解前会在本地遮盖可识别的姓名、电话、邮箱等字段，交给模型的是处理后的文本，不是原附件。这不代表后续所有聊天与任务内容都完全匿名，具体联网边界见第07章。

如果 PDF 是扫描图片、提取不出完整内容，按提示粘贴文本。系统不应把“文件上传成功”当作“里面的经历已经准确读出”。

### 第二步：整理画像和匹配卡草稿

模型依据简历组织基本背景、经历、能力和方向；程序检查输出是否符合所需结构，再保存为本地资料。

画像已经保存、匹配卡生成又失败时，现有流程还可从已保存的项目与技能摘取本地卡片草稿供你检查，不凭空补能力。画像、卡片和方案各有保存阶段；方案失败时，应从未完成阶段继续，不必丢掉已整理的画像。

匹配卡中可检查的内容包括：

- **目标方向**：哪些工作方向值得寻找。
- **强证据**：你确实做过的工作，以及原简历依据。
- **可迁移能力**：可以支持相近工作的能力，以及尚未证明的部分。
- **需谨慎转向**：与现有经历差距较大的方向及原因。
- **用户补充偏好**：你的意愿和限制。这些偏好用于匹配，不会直接发送给招聘方，也不能代替经历证据。

### 第三步：生成搜索方案

系统把求职方向变成可用于搜索的方案，再由你核对城市、薪资、经验与关键词等设置。

搜索词是寻找岗位的入口，不是最终能力判定。自动方案优先组织“后端开发工程师”“AI 应用工程师”等岗位名称，避免把单独技能名、项目名当成职位。初次推荐的薪资筛选留给用户填写，不替你猜工资。最终仍要看完整 JD，不能把搜索词命中当作能力已匹配。

### 第四步：你确认，系统才使用这套依据

打开匹配卡草稿，修正误解后先 **保存草稿**，再点击 **确认匹配偏好卡**。已准备好的同画像方案可随之启用；继续检查方案，需要调整时再保存。

确认新卡会替换此前的已确认卡，旧卡保留为历史。基于旧卡的方案需要重新保存，避免“页面上看的是新能力，后台仍按旧依据找岗”。

完成后，应能看到已保存的资料、已确认的匹配卡和可使用的搜索方案。保存或确认这些资料不会自动发起沟通。

## 4. 核对时到底看什么

重点检查影响判断的理解，不必为了“字段填满”补充无关信息。

| 系统整理的内容 | 怎么判断 |
| --- | --- |
| “独立负责整个产品” | 原简历只支持负责某个模块时，要收回到实际责任 |
| “具备接口开发经验” | 若有对应工作事实，可以作为直接依据 |
| “愿意转到算法研究” | 这是求职意愿，不代表已经具有算法研究经历 |
| 正常完整简历只列本科 | 按本科理解，不凭空猜测还有隐藏硕士学历 |
| 没写全日制 | 不应仅凭这一省略制造拒绝理由，也不能把它写成已经核验的承诺 |
| 不同但相关的专业 | 结合岗位工作与实际项目看相关性，不只比较专业名称 |

例如，你写了“希望找 Agent 应用开发”，系统可以据此寻找这个方向；但应继续看你的真实开发工作能对应哪些职责，不能只因为你想做，就把所有相关能力都标成已经掌握。

## 5. 搜索条件与平台页面如何配合

**搜索方案是本地意图，平台页面是实际执行范围。** 两者都需要清楚。

开始前，在 **今日任务** 检查当前平台搜索条件。平台原有的城市、经验、学历等筛选可能仍然生效；按页面提示读取或调整实际条件，避免你以为在看一个范围，平台实际返回另一个范围。

使用继承平台当前条件的路径时，系统保留现有搜索范围并按任务替换关键词，不应把关键词变化理解为所有平台筛选都会重置。不同平台提供的条件和读取能力也有差别。

平台筛选负责限制能被发现的岗位范围，完整 JD 分析负责判断已经取得的岗位是否值得争取。如果平台前面就过滤掉某类岗位，后面的模型看不到它，也无法替你找回来。

## 6. 之后为什么通常不用重新上传

资料、匹配卡和方案会保存在本地。下一次应从已有方案进入，启动新一轮找岗。

相同简历已有可用结果时，现有流程可以复用资料；资料变动或明确刷新时，才重新生成相关结果。具体旧判断是否失效，由它使用的简历、匹配依据和分析版本决定，见 [02 岗位判断](02-job-discovery-and-matching.md)。

如果只是尚未确认匹配卡，应打开现有草稿确认，不必重复上传同一份文件。若当前没有看到旧资料，先核对是否启动了另一份数据目录。

## 7. 交给 Agent 使用时，有什么区别

普通用户在页面里操作并配置模型服务；委托外部 Agent（可受托执行操作的 AI 助手）时，由 Agent 走无界面命令行入口，并直接提供模型回答，不要求用户去页面中配置一个“Agent 提供商”。

两种入口共用求职规则；指向同一数据目录时才能共享实际资料。Agent 确认匹配卡、执行只读找岗，也不等于已经获得代你联系 HR 的授权。

命令细节放在 [Agent 操作说明](../agent-operation.md)，不影响普通用户按本章完成首次使用。
