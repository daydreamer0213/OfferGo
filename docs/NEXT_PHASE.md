# OfferGo 当前后续工作

> 核对日期：2026-10-02。本文只列当前可执行的下一步，不把旧验收记录当作现状。2026-09-10 以前的主控索引保存在[历史索引](NEXT_PHASE_2026-09-10.md)。当前版本边界见[项目交接](PROJECT_HANDOFF.md)。

## 恢复验收与发布时的顺序

1. **先确定验收对象。** 公开 v1.3.2 安装版与当前 OfferGo 源码不是同一功能基线。新源码应先冻结提交、运行该提交的完整离线和浏览器门禁，再创建隔离的安装验收环境；不能用旧安装版、旧端口或旧数据库证明新功能。
2. **按真实用户路径检查。** 对当前源码构建出的新安装版，从桌面或开始菜单图标启动，在 Edge 里检查首次使用、单/双平台找岗、消息同步及页面反馈；Agent 路径则按[无界面操作说明](agent-operation.md)从 CLI 检查。真实 BOSS、智联页面是否仍适配，以当次只读页面证据和运行结果为准。
3. **外部写入另行确认。** 真实沟通、发送回复、发送简历和投递必须针对具体目标取得用户授权，并依 [AGENTS.md](../AGENTS.md) 的身份核验与停止规则执行。完成只读验收或通过离线测试都不自动授予发送权限。
4. **准备新版本发布前核对版本号。** 仓库 `package.json` 仍为 1.3.2，但当前 `BuildInstaller.bat` 会生成 OfferGo 名称的新安装器。先区分已公开的 RoleFlow v1.3.2 与待发布源码，再确定版本号、资产名称和发布说明，避免同号不同功能的包混淆。

改到数据目录、平台操作、消息发送或用户页面时，要同步更新现行文档；历史发布说明和验收记录保留原貌。文档修订不代替上述验收。架构演进应按[当前架构](architecture.md)中的现存边界逐项处理，不按旧索引重启已经完成的阶段。
