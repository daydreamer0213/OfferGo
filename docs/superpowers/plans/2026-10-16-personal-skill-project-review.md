# OfferGo：用个人 Skill 做项目审查的计划

日期：2026-10-16。状态：首轮审查已完成，见[审查结果](../reports/2026-10-16-personal-skill-project-review.md)。产品问题尚未修复，原四步整体验收的未决事项保留。

这次要回答三个问题：项目现在能否帮助用户顺畅求职；生成的内容是否真正有用；距离原定验收完成，还剩哪些具体问题。审查沿用[原四步验收](2026-10-09-four-step-acceptance.md)的顺序，用现有成果确定起点，再补必要证据。

本文件记录审查方法，不改动产品，也不把文档里的历史通过记录算作今天重新验证通过。当前核对的源码工作区为 `codex/acceptance-checkpoint-20261015`，提交 `da6cfba`；实际体验入口、运行版本及所用数据在执行前确认。

## 二、从已有成果开始

根据当前验收清单与专项报告，以下是本次计划的起点，执行时只核对与当前版本有关的部分。

| 已有记录 | 审查时怎样处理 |
| --- | --- |
| 平台消息同步、搜索页恢复、重复页处理及部分正常页面入口已有证据 | 先确认后续变更是否影响对应路径；未受影响就引用原证据，不整轮重做 |
| 回复、简历、连续面试已有实际输出；故事准备和分段简历编辑近期交付 | 阅读实际成稿及对应流程，优先查用户能否直接使用；区分自动生成原稿与人工修订稿 |
| 当前筛选结果及候选入口已有有限审查记录 | 复用当前规则下的有效结果；先确认语义版本，不清空已有数据来制造新一轮任务 |
| 资料更正、保存重开和局部恢复已有受控证据 | 针对未覆盖或被变更影响的衔接补验，不把一次重开推广为所有模块都通过 |
| 求职体检的完整旅程已有合成案例，当前真实方案缺少联系反馈 | 可检查建议链路是否合理、页面是否好用；自然求职效果另记，不能凭空补造 |
| 智联一次历史发送结果仍无法确认 | 保留未知结论与原记录，列为独立未决项；不通过重发来消除未知 |

当前整体四步验收仍未全部闭合。此次审查的价值，是把剩余问题变成可处理的小清单，而不是再积累一批“检查过”的记录。

## 三、执行顺序与通过条件

### 准备：锁定本次审查对象

**检查方法：**读取当前四步清单的最新检查点、最近变更和直接相关报告；确认运行入口、源码版本、资料版本及是否为隔离数据。检查代码时沿当前实际调用路径定位，不扫描全部代码找理论问题。

**产出：**在一份审查记录里列出四步各自的“已有有效证据、受变更影响、尚缺证据”，每个结论附出处。旧证据无法关联当前版本时，准确写出缺哪项关联。

**结束条件：**每项待查问题都对应一个用户任务及下一项检查。只因记录缺失，不能先判产品有问题。准备工作预算约 30—45 分钟。

### 第一步：核对真实平台流程的剩余缺口

**用户任务：**找到机会、看懂详情、读取 HR 消息，并正确识别下一项可操作的事。

1. 对照原第 1 步，复用已有消息同步、搜索条件和重复页治理证据，确认相关代码之后有没有改变。
2. 查看现有正常入口能否把岗位、完整 JD、消息和操作准备关联到同一目标；只补缺失或受影响的一段。
3. 历史未知发送单列记录。需要实际页面补证时，先明确只读核验能回答什么，再按当前项目规则做最小检查；本计划不安排新的发送或投递。

**通过条件：**所审范围的岗位身份、资料和用户操作一致；异常有准确状态与恢复入口。无法查清的历史外部结果保留为未知，不因此机械重放，也不妨碍继续审查独立模块。

**结束条件：**形成“可复用通过项、具体缺口、未知项”三类结论，预算约 30—45 分钟；需要平台等待时保留现场，继续本地独立检查。

### 第二步：检查核心内容到底好不好用

这一阶段优先阅读现有实际结果。缺乏当前版本的有效样本时，才对明确缺口补一次产品生成；保存第一次输出，审查者的改写不计作产品能力。

| 模块 | 怎样检查 | 可接受结果 |
| --- | --- | --- |
| HR 回复 | 复用已有多背景、多意图证据，精读约时间、索要简历、追问经历各一份实际草稿；对照 HR 原文和本人资料 | 回答对方这次的问题，事实准确、语气自然；简历邀请有对应动作，不能只答“可以发送”；已知事实不反复问 |
| 面试准备 | 先按简历各主要职责核对故事覆盖，再精读三个不同难度的故事及两条深入追问；分别查看自动原稿、人工修订稿 | 产品先提供可编辑故事；责任、问题、做法、选择理由、结果与经验连贯。未知细节可请本人补充，不能编造。通用项目故事与深入追问是主线，岗位定制为补充 |
| 面试反馈 | 阅读已有完整训练中的合格回答和有明确缺口的回答各一例，连同追问、反馈、整轮报告一起看 | 已答清的内容不再机械要求重答；真实缺口能说清哪里不足、怎样回答更好；不能只因出现关键词就算答好 |
| 简历修改 | 完整阅读现有通用、定向成稿各一份；对照原简历与实际分段编辑入口 | 沿简历原章节和项目组织，优先改善项目、经历和技能的表达；不凭空改变学历、成果或个人事实；有完整可编辑结果，原版本保留 |
| 求职体检 | 查看反馈不足、已有明确反馈两种现有样本，沿“实际记录→判断→建议→修改入口”检查 | 样本不足时不下武断结论；有依据时能指出哪段内容为什么值得改、怎样改，避免机械地按指标扣分；合成案例与自然效果分别记录 |
| 页面与用户指南 | 随上述流程对照对应指南，连续阅读实际页面，检查重点、展开内容和按钮；明显拥挤处查看实际画面 | 用户先看到当前任务和可用结果，文字具体、有层次；操作名称与真实界面一致；必要提醒有具体影响，删去无行动价值的责任切割 |

**关键判例：**“语义和关键词检索提供不同角度材料”仍然太笼统。合格解释应能讲清：语义检索有助于找到措辞不同但意思相近的内容；关键词检索有助于抓住型号、术语等需要准确匹配的内容；随后解释这个项目为何需要两者及怎样处理候选。机制知识不能被写成候选人确实做过的实现。

**结束条件：**每个模块都有实际成稿或流程结论，具体问题标出位置与影响；预算约 90—120 分钟。未发现问题也可正常通过，不以“必须提出优化”作为审查成果。

### 第三步：按现实求职标准审查岗位筛选

**判断标准沿用用户已经确认的尺度：**真正合适的机会不漏掉，明显不合适的岗位不进入默认投递候选；有实际相关经历但存在差距的岗位，允许继续尝试。

1. 先核对简历、JD 全文、当前规则和保存结果的版本；复用规则变更后仍有效的现有结果，不为了此次审查重分析全部岗位。
2. 在查看产品结论前，审查者独立阅读选定材料并记录理由。首批共选约 6—9 份有完整 JD 的材料，其中两份按第 4 项抽取；其余覆盖明确合适、明显不合适、相关但有差距三类。选材包含已有排除结果中的相关岗位，不能只看推荐列表。
3. 重点检查相近专业、缺少“全日制”字样、技术框架不同但职责相关，以及明确必要条件冲突。一般缺省信息按正常简历情境处理，不把初筛做成录用资格审查，也不虚构未列出的学历。
4. 逐份比较机会是否被保留及理由是否贴合 JD 主体工作。在典型边界之外，从剩余有效材料随机抽取两份复核项，计入首批 6—9 份总量；抽取时不查看产品结论。复核不证明全市场统计表现。
5. 样本仍缺关键类型时，优先从已保存完整材料补足；确需新采集时只取必要小样本。只有筛选语义发生实质变化，才建立新的空操作基线；保留原简历、方案、设置及旧数据。

**通过条件：**检查范围内无可确认的合适机会误排、明显不合适机会默认入选；模糊岗位不强求唯一等级。说明能解释具体工作关联与差距。抽样发现误判时记录原始结果、影响和根因，不反复改标签直到结果好看。

**结束条件：**用样本得出有限、可说明的结论及必要修改项，预算约 45—60 分钟。小样本不能换算整体漏投率，也不能把正式找岗积压数量变成本轮软件验收门槛。

### 第四步：检查连续使用能否接得上

以准备阶段找出的证据缺口为准，每种缺口只选一个代表流程；已通过且未受影响的部分直接复用。

1. **草稿接续：**从正常入口编辑并保存，离开后重新打开，核对文字、版本和后续动作；优先覆盖尚缺证据的回复草稿，而非再次只验招呼。
2. **资料更正：**选择一条已确认资料的更正或撤回，核对保存状态及下一项相关任务的实际输入；已有同一路径有效证据时不新增模型调用。未确认编辑不能提前变成正式事实。
3. **中断恢复：**选择当前未证明的暂停、退出重开或条件变化路径，检查是否接住已有任务、保留结果、使用正确条件，不重复执行外部动作。
4. **等待与失败：**从用户实际画面判断能否看出正在做什么、是否已保存，以及失败后怎样继续，避免让用户反复询问“卡了？”才能知道状态。

**通过条件：**检查范围内无资料丢失、旧事实错误传播、状态误导或重复动作，用户能从正常入口接续任务。

**结束条件：**每个缺口得到通过、确认缺陷或明确缺少的证据，预算约 45—60 分钟。一周自然使用和长期休眠另列观察，不延长本轮审查去等待，也不把短期实验说成长期效果已通过。

## 四、每个阶段如何复盘、如何防止跑偏

- 每完成上述一个阶段，就简短汇报：本阶段确认了什么、留下什么具体问题、对整体交付有什么影响、接下来查什么。
- 连续两轮围绕同一局部问题而没有新增有效结论时，停止第三轮机械重复。先确认它是否仍阻挡用户核心任务，以及下一轮究竟能获得什么新证据；没有明确答案就换到更有价值的缺口。
- 对已通过项，只有需求改变、相关代码改变、实际失败或会影响决定的新疑点，才重新打开。
- 审查发现问题先记录、排序；不边看边扩成重构、模型对比、全量重生成、发布打包或平台整轮重跑。实际修复另列范围，按问题所需做调试与验证。
- 委派只用于独立核对或复读，提供本计划、用户表达规范、具体资料和预期结论；一个人负责整合判断。平台操作始终串行。

问题分三档：

| 优先级 | 什么情况下属于这一档 | 下一步 |
| --- | --- | --- |
| 必须先解决 | 阻断正常核心任务、丢失资料、错误外发风险、虚构关键事实，或确认的重大筛选误判 | 给出可复现问题、最小修复范围与复验方法；明确受影响流程 |
| 影响使用，应优先改善 | 能完成任务，但关键内容笼统、难懂、答案质量差或流程明显绕路 | 按用户影响排序处理，不把它弱化成纯美化 |
| 后续优化或观察 | 不影响当前约定任务的措辞偏好、理论边界、尚未到来的自然反馈 | 记录具体价值；不作为当前阶段无限悬挂的理由 |

## 五、交付物和本轮结束条件

只维护一份审查报告，放在现有 `docs/superpowers/reports/` 下；每项包含“用户任务→实际结果→证据与版本→判断→建议动作”。必要私有资料放 D 盘隔离目录，报告只引用去标识后的结论。

最终交付：

1. **当前能力与缺口表：**原四步中哪些可复用、哪些本次补证、哪些还未解决。
2. **按影响排序的问题清单：**每个问题有具体位置、实际影响和最小下一步，不堆泛泛的“建议优化”。
3. **下一阶段建议：**先修哪些问题、哪些可直接交用户体验、哪些需要未来真实反馈，以及对应的完成条件。

首轮审查按约 4—6 小时有效工作量控制，属于审查预算，不是整个项目完成时间承诺。超出预算时先汇报新增问题和剩余工作，不默默扩成多日调试。修复工期根据确认的问题另估。

本轮结束于：上述四步均形成有依据的结论，主要缺口有明确后续动作；不以全绿、找出指定数量的问题，或等待一周自然反馈作为结束条件。原四步验收是否完成，仍按其各自条件判断；本轮审查结束不等于整个项目验收通过。
