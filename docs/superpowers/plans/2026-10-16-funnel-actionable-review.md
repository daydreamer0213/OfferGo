# 求职体检：用实际反馈指导下一步

**Goal:** 指标定位停滞环节，已有 HR 原话支持具体检查，用户能看到依据、先做什么和之后观察什么。

**Architecture:** 沿用现有漏斗统计、等待与未知规则、按平台生效的策略轮次。只读关联当前样本的本地对话、岗位和当时记录的简历版本，生成可追溯的检查建议；不新增模型、数据表或自动采集。

## 已确认设计

- 单条具体反馈不受30个样本门槛限制；统计趋势继续遵守既有样本保障。
- 引用保存的 HR 原文，按已有分类组织主题，不把主题、关键词或追问本身判成拒绝原因、能力缺失或简历缺陷。
- 同一岗位/会话/消息去重；平台、候选人、方案、当前有效轮次及消息时间必须匹配。旧轮次的晚到反馈仍归旧样本。
- 岗位要求是当前本地记录，简历版本是本地当时绑定，均不冒充平台实际阅读/发送版本。只有成功的简历动作才说明已执行发送动作；索简历与发简历、约面分开。
- 单纯问薪资/时间只提示核对条件；项目问题先核对实际回答和对应项目；拒绝但无理由则显示原因未明确。面试后无结果先核对进展，不补造技术失败原因。
- 每次优先一项检查，保留其他方案与版本；观察后续同类机会的回复、约面与最终进展，不为提高比例擅自收紧筛选。
- 没有可引用反馈时，旧指标仅给待检查方向；固定比例是内部提醒线，不是行业合格线或已证因果。

## 实施与验收检查点

1. **证据关联**：独立存储 helper + 合成回归，验证身份/轮次/时间/方向/历史版本和发送动作的正确边界。
2. **建议和页面**：小的纯函数组织具体反馈与面试后进展；保留比例提示并解释限制。页面清楚区分“看到什么 / 先检查什么 / 原话依据 / 下一步观察”，可以进入原对话、简历工作室或面试记录。先写失败回归再实现。
3. **真实使用检查**：合成浏览器旅程覆盖小样本项目追问、薪资问询/明确拒绝、面试后未知/已有 Offer、混合平台、无原文及重复消息；检查导航、窄屏和明暗色，不产生外部动作。
4. **复核收尾**：独立审查、相关回归、D盘副本查看现有数据实际效果，保留原内容与既有面试/简历能力，展示用户可使用页面并保存代码。

每阶段回顾：新增的建议是否有可点开核对的依据，用户是否知道先做哪一件事，是否把观察误写成原因。没有新的实际问题，不继续扩通用语义分类器或统计实验。此轮不替代原四步整体验收。
