# 原样保存方案的模型版本一致性修复

> **For agentic workers:** 按已确认整改目标执行有限修复；先失败回归，再最小实现，最后实际页面与准确版本验证。

**Goal:** 普通用户原样保存筛选方案时，保留仍符合当前材料和模型的有效分析；真实资料、条件或模型变化仍让旧判断失效。

**Architecture:** 复用 Dashboard 已有 `getRuntimeModel("batch_screening")` 和运行时缓存。方案保存先检查活动任务；无活动任务才以实际批量筛选模型覆盖基础配置并执行既有 `profileToRuntimeConfigs` / `rescorePlanObservations`。

**Tech Stack:** 现有 Node.js、SQLite、Dashboard 和 Edge；不增加依赖。

## 已确认前提与范围

准确产品源码 `04a03b2f0e4616418a4a1c1b34dbaab491f52ee9` 的真实资料独立副本，当前 11 岗、9 完成分析、2 失败。9 份完成分析原有模型指纹均与 Data 中实际批量筛选模型相同。普通 Edge 原方案零字段改动保存一次，POST 303 后 9 份均失效，唯一原因为 `model_inference_changed`；资料、确认卡、简历全文、模型设置和缓存未变化。

源码的保存路径独立读取 `loadConfigs(root).model`，本例为默认离线模型；实际分析从 `dataRoot` 的批量筛选设置取模型。该不一致会让有效结果退出推荐池、要求不必要的重新分析，不只是解释措辞问题。

第一尝试在任何服务/浏览器/提交前因检查工具的 SQLite 对象形式比较失败；只修工具的内容比较后沿用同一副本续接。源资料未变，实际业务保存总数仍为一次。私有证据保留于 D 盘，不放入 Git。

## 设计选择

选择复用已有运行时模型函数：与实际分析保持同一来源、任务配置、模拟测试行为和缓存。另在 handler 直接解析 Data 会重复读取并绕过现有注入与缓存；继续使用静态模型则不能解决已复现问题。

- 只改内部保存路径和对应现有回归测试，不改匹配提示、推荐档位、覆盖或风险节奏。
- 保存方案仅作本地版本核对，不要求模型连接就绪，不发模型请求。
- 活动任务的延期重算保持；该分支不额外解析模型。
- 模型未配置或凭据不可读时沿用现有解析结果；不通过猜测静态 mock 掩盖设置文件错误。
- 正常资料变化、条件变化、模型变化的过期规则保留；不直接改旧结果推荐。
- 原工作台、原操作库、外部发送和不确定历史动作不变，不发布。
