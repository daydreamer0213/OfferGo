# OfferGo 导航、设置性能与双平台调度设计

**状态：** 用户已确认

## 目标

解决三个直接影响使用体验的问题：已有筛选方案时各页面左栏保持一致；“模型与设置”页面不再为了显示页面而同步解密 API Key；同时使用 BOSS 与智联时，调度现有的两条单平台流程并行采集。

## 设计约束

- 复用现有 BOSS、智联 workflow、CLI 扫描、分析队列和状态页面，不新建第三套扫描模式。
- 单平台入口、URL、暂停、停止、恢复和安全节奏保持兼容。
- BOSS 内部仍然串行，智联内部仍然串行；只有两个平台之间可以并行。
- 模型分析沿用现有任务队列，并受同一个批量筛选并发上限约束。
- 不改变沟通和投递授权边界。

## 一致导航

Dashboard 从数据库中解析最近使用的有效筛选方案，作为设置页、招聘平台页和诊断页的导航上下文。存在方案时，三个工具页也显示完整导航，并携带 `planId` 与当前平台返回工作台。求职体检属于跨平台统计，因此在智联上下文中也显示。没有任何方案的首次使用阶段继续显示精简导航。

## 设置页快速打开

页面首屏只读取模型设置文件和加密 Key 文件是否存在，不在 GET 请求中启动 PowerShell 解密。已保存的连接验证结果照常显示，API Key 明文不进入页面。实际运行模型时仍通过现有 runtime cache 解密和校验；保存、删除或更换 Key 后继续清空 cache。这样删除或损坏的 Key 不会被误用于模型调用，同时页面打开不再承担约两秒的进程启动成本。

## 双平台调度

页面在 BOSS 与智联都启用时提供“同时运行 BOSS + 智联”。这个入口把同一个 `planId` 分别交给现有 `start({site:'boss'})` 与 `start({site:'zhaopin'})`，并行等待两个启动结果。每个平台仍创建自己的 workflow、scan run、batch、lease 和检查点。

原有全局互斥改为按平台互斥，同一平台仍拒绝重复运行。内存运行键加入平台，避免同一方案的两个子进程互相覆盖。分析任务继续走现有数据库任务领取逻辑；领取时增加全局运行中任务计数，使两个进程合计不超过已配置的批量筛选并发数。

两个平台独立报告结果。一个平台启动失败时，另一个已经启动的任务继续运行；页面明确显示两个结果，不回滚或停止成功的平台。重复点击会返回各平台现有的活动 workflow，不重复创建任务。

## 验证

- 有方案时，今日任务、招聘平台、模型设置和运行诊断显示同一组完整导航；首次使用仍可使用精简导航。
- 模型设置 GET 不调用凭据解密，保存与真实模型调用仍会验证 Key。
- 单平台测试保持通过。
- 双平台入口确实调用两次现有 start，允许不同平台 lease 并存，同平台 lease 仍冲突。
- 同一 `planId` 的 BOSS 与智联运行记录不互相覆盖。
- 两个 workflow 同时分析时，数据库中未过期的 running 任务总数不超过配置并发。
