# OfferGo 通用 Agent 模型通道设计

2026-09-16。用户希望 OfferGo 同时支持两条正式使用路径：用户可以填写模型 API Key 直接使用，也可以让本机已经登录的编程 Agent 下载并运行项目，在 OfferGo 中不填写 API Key，直接使用该 Agent 的账号能力。用户确认 Agent 指 Codex、Claude Code、Kimi 等本机 Agent，并进一步确定不为每个 Agent 复制业务适配；OfferGo 应只维护一个通用接口，各 Agent 只保留必要的薄启动差异。第一版使用 Codex 验证通用接口。

## 目标与边界

- API Key 模式保持现有能力、设置和加密保存方式，不因新增 Agent 模式而降级。
- Agent 模式覆盖现有全部模型任务，包括简历解析、搜索方案、匹配偏好卡、岗位理解、岗位匹配、沟通草稿、定向简历优化和模拟面试。不能出现“首次使用免 Key，但后续某个功能仍要求 Key”的半通状态。
- Agent 模式只复用本机 Agent 已有的登录状态，不读取、复制、展示或保存 Agent 凭据。
- “免填 Key”不表述为免费。页面说明该模式会消耗用户 Agent 账号的套餐额度，并会把当前任务所需的简历、JD 或回答发送给该 Agent 对应的模型服务。
- 第一版内置 Codex 启动器。通用协议不依赖 Codex；以后支持其他 Agent 时，只新增协议启动器和兼容性检查，不复制提示词、输出校验或产品工作流。
- 不自动安装 Agent、不代替用户登录、不从 Agent 配置中提取密钥、不在浏览器表单中接受任意可执行命令。
- Agent 只承担模型推理，不获得招聘浏览器控制权，也不改变 BOSS/智联的读取、人工确认和发送安全边界。

## 用户路径

“模型与设置”顶部增加“模型使用方式”：

1. **使用 API Key**：沿用当前共享厂商、独立凭据、主模型和备用模型设置。
2. **使用本机 Agent**：不显示 API Key 输入框，显示检测到的 Agent、登录检查、一次安全测试和套餐额度说明。

Agent 模式首次进入时自动检测受支持的启动器。检测结果分为：

- 可使用：命令存在、所需能力存在、非敏感测试返回有效结构。
- 需要登录：命令存在，但账号未登录或授权已失效，给出准确的登录操作。
- 需要更新：命令存在，但不支持 OfferGo 所需的非交互、临时会话或结构化输出能力。
- 未安装：给出官方安装入口和命令，不静默安装软件。
- 暂时不可用：额度、网络或服务异常，保留已有本地数据并给出重试入口。

测试成功后保存的是 `mode=agent`、`runnerId=codex`、已验证时间、启动器能力指纹和非敏感模型身份，不保存登录凭据。深度分析和批量筛选第一版共享同一个 Agent 启动器；产品仍保留两个任务配置身份，以便记录各自超时、重试和模型修订。运行中的工作流固定使用启动时冻结的模型通道和修订，用户改设置不会改变正在处理的任务。

Agent 失败时不自动切换到收费来源不同的 API Key，也不从 API Key 自动切换到 Agent。页面让用户修复当前通道，或明确切换后重新开始/继续允许恢复的任务。

## 架构

当前 `OpenAICompatibleAdapter` 同时包含业务提示词、任务编排、契约修复和 HTTP 调用。实现前先做一次保持行为不变的拆分：

```text
OfferGo 工作流
  -> StructuredModelAdapter
       - 现有任务方法与提示词
       - 输入准备、结果校验、契约修复
       - 任务级重试规则
       -> ModelTransport.requestJson(request)
            ├─ OpenAICompatibleTransport
            └─ AgentCommandTransport
                  -> runner: codex
```

`StructuredModelAdapter` 是唯一的产品模型接口。它继续暴露当前方法，并复用现有 `validateModelResult`、拆分匹配和证据边界。传输层只负责把一条结构化请求可靠地交给模型并取回一个 JSON 对象，不理解求职业务。

现有 API 模式迁移到 `OpenAICompatibleTransport`，HTTP 地址、Bearer Key、JSON mode、token 限制和上游错误映射保持原行为。第一阶段拆分完成后，现有离线测试必须原样通过，证明没有借新功能改变匹配质量。

## 通用 Agent 协议

OfferGo 与启动器通过子进程标准输入/标准输出通信，不通过 shell 拼接命令。请求是一个 JSON 对象：

```json
{
  "protocolVersion": 1,
  "requestId": "opaque-id",
  "taskKind": "analyzeResume",
  "systemPrompt": "...",
  "input": {},
  "outputSchema": {},
  "limits": {
    "timeoutMs": 120000,
    "maxOutputBytes": 1048576
  }
}
```

成功响应：

```json
{
  "protocolVersion": 1,
  "requestId": "opaque-id",
  "ok": true,
  "result": {},
  "identity": {
    "runner": "codex",
    "model": "reported-or-default",
    "runnerVersion": "reported-version"
  }
}
```

失败响应使用 `ok=false`，只返回稳定错误码、可操作说明和 `retryable`。协议错误、请求编号不一致、非 JSON、超大输出或多余输出均拒绝，不能猜测为成功。标准错误不作为业务结果。

通用接口允许未来的 Agent 使用任何内部调用方式；OfferGo 只要求启动器遵守协议。因此新增 Agent 的工作限于命令定位、参数构造、登录/能力检查、最终消息提取和错误翻译。

## Codex 启动器

第一版启动器通过 `execFile` 或等价的无 shell 子进程 API 调用 `codex exec`。实现时以能力探测决定是否可用，不只比较版本字符串。需要验证的能力包括：

- 非交互执行；
- 临时会话，不把简历和 JD 留在可恢复会话中；
- 独立空工作目录；
- 忽略该目录和用户配置中的项目规则、Skills、MCP 与自定义命令；
- 只读沙箱，不允许修改文件；
- 结构化输出或可唯一提取的最终消息；
- 可响应取消和超时。

每次调用在 OfferGo 数据根目录下创建一个仅供该请求使用的临时目录，写入必要的输出 Schema，不写入提示词、简历或 JD。完整请求只走子进程标准输入；最终结果优先写到受控输出文件或从结构化事件中提取。完成、失败、取消或进程退出后清理临时目录。

启动器不使用批准绕过参数，不给 Agent 添加项目目录，不允许它控制招聘浏览器。工作目录为空、会话临时、规则隔离和只读沙箱共同缩小提示注入可能造成的动作范围；业务提示词继续把简历、JD 和 HR 原话标记为不可信数据。

如果当前 Codex 版本无法同时满足这些隔离能力，Agent 模式显示“需要更新”或“当前版本不受支持”，不能降低隔离要求后继续。

## 并发、幂等与恢复

- 每个本机 Agent 启动器使用一个串行队列。相同任务标识和相同模型修订的在途请求合并，不重复消耗额度。
- 不同请求按提交顺序执行。队列长度和当前任务只保存在运行状态中；持久工作流仍依靠现有 SQLite 任务、租约和检查点恢复。
- 页面刷新或重复点击不能创建重复 Agent 进程。已有请求完成后，调用方从同一结果继续。
- 用户暂停、工作流取消或服务关闭时，先发送取消信号；宽限期后终止子进程树，不能遗留后台 Agent。
- 登录、配置、协议和契约错误不自动重试。临时网络或上游繁忙只使用现有有界重试预算。一次契约修复仍算一次明确的新模型调用，并记录原因。
- Agent 退出结果不明确时，本次模型任务标记为失败/待恢复，不能把部分标准输出当成成功结果。

## 错误与诊断

Agent 错误映射到现有模型错误体系，并补充稳定错误码：

- `MODEL_AGENT_NOT_INSTALLED`
- `MODEL_AGENT_UPDATE_REQUIRED`
- `MODEL_AGENT_AUTH_REQUIRED`
- `MODEL_AGENT_QUOTA_EXHAUSTED`
- `MODEL_AGENT_TIMEOUT`
- `MODEL_AGENT_CANCELLED`
- `MODEL_AGENT_PROTOCOL_INVALID`
- `MODEL_AGENT_PROCESS_FAILED`

诊断日志只记录请求编号、任务类型、开始/结束时间、耗时、启动器、非敏感模型身份、退出码和稳定错误码。不得记录请求 JSON、提示词、简历、JD、聊天内容、标准输出正文、原始标准错误或 Agent 凭据。为排查兼容性可以记录经过允许列表过滤的能力探测结果。

## Agent 下载并运行项目

仓库增加一份短而确定的 Agent 安装说明，让用户把 GitHub 地址交给 Agent 后，Agent 可以按固定顺序完成：

1. 下载项目并确认受支持的 Node、Edge 和操作系统条件；
2. 把依赖和较大生成数据放在合适的数据盘/项目目录；
3. 运行离线检查和安装自检；
4. 检测执行安装任务的 Agent 是否也能作为 OfferGo 模型启动器；
5. 启动 OfferGo，并把用户带到“使用本机 Agent”的连接测试；
6. 不读取或回显任何已有凭据，不替用户登录招聘平台，不执行消息发送。

该说明服务于 Codex、Claude Code、Kimi 等安装 Agent，不把安装 Agent 的名称写进产品数据。安装完成后，OfferGo 只依赖已保存的 `runnerId` 和运行时能力检查。

## 测试与验收

离线测试使用假启动器，不调用真实账户，至少覆盖：

- API Key 模式拆分前后输出与错误行为保持一致；
- Agent 协议成功、非 JSON、错误请求编号、超大输出、非零退出和标准错误污染；
- 未安装、需更新、未登录、额度耗尽、超时、取消和服务关闭；
- 同一请求合并、不同请求串行、刷新/重复点击不重复启动；
- 敏感输入只经标准输入传递，日志、进程参数、设置 JSON和数据库均不出现简历/JD/Key；
- 全部现有模型任务经过同一个假 Agent 通道并通过原有契约校验；
- API 与 Agent 模式切换不改变运行中工作流的冻结修订；
- 安装包包含启动器和说明，源代码安装与安装版都能完成能力检查。

真实 Codex 验收先使用合成简历和合成 JD，不访问招聘平台：完成连接测试、简历画像、搜索方案、匹配卡、岗位理解与匹配、沟通草稿、简历优化和模拟面试。确认不会修改文件、不会创建可恢复 Agent 会话、不会把输入写入日志，并核对暂停/取消没有遗留进程。通过后再由用户使用真实资料进行人工验收；该验收不包含自动发送招聘消息。

## 完成标准

- 新用户在本机 Codex 已登录且能力检查通过时，可以不填写任何模型 API Key，完成 OfferGo 全部模型功能。
- 未安装、未登录、版本不兼容和额度不足都有明确下一步，本地历史数据仍可查看。
- API Key 用户的现有设置、加密保存、模型质量和工作流行为没有回归。
- Agent 任务不能操作招聘网页、修改项目文件、读取项目规则或静默切换计费通道。
- 新增第二种 Agent 时不修改 `StructuredModelAdapter` 或任一求职业务提示词，只增加一个符合协议的薄启动器和对应兼容性测试。
