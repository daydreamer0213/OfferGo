# Agent 直接运行 OfferGo：无界面设计

## 用户路径

OfferGo 保留两条互不混合的使用路径：

1. 普通用户启动本地页面，在模型设置中填写 API Key。
2. 用户把项目交给一个已可用的 Agent。Agent 在终端安装并运行 OfferGo，用户不打开前端，也不填写 Key。

第二条路径中的 Agent 是项目操作者和模型本身。OfferGo 不应再启动 Codex、Claude Code 或 Kimi 子进程，也不应在前端保存“Agent 模式”。

## 通用接口

Agent 路径使用单一的 stdio JSON 行协议。Agent 用 `run.ps1 ... --agent` 启动无界面命令。OfferGo 每次需要模型判断时向标准输出写一行请求；当前外层 Agent读取请求，在标准输入写回一行响应。所有 Agent 使用相同协议，不增加厂商适配器。

请求包含协议版本、任务 ID、任务类型、约束指令和输入。响应必须携带同一个任务 ID 和一个 JSON 对象结果。OfferGo 继续使用已有模型契约校验结果；不匹配 ID、无效 JSON、过大响应、超时、取消或 Agent 明确报错都立即停止当前任务。

同一进程中的请求必须串行，避免多个交互任务同时等待同一个标准输入。请求和响应只存在于当前进程，不写入模型设置，不创建可恢复 Agent 会话。

## 首次使用

Agent 每次开始使用时运行 `agent-onboard --resume <path> --operation-id <uuid> --agent`。OfferGo 本地解析并遮盖简历隐私。首次使用或简历变化时，通过 stdio 依次请求候选人画像、匹配偏好卡和搜索计划，校验并保存到隔离数据目录；简历内容未变化时直接复用完整的已有结果，不发模型请求。完成后终端返回完整匹配卡、搜索计划及其 ID；Agent 检查后用 `agent-confirm` 确认匹配卡。

幂等与业务复用分开判断。操作 UUID 只标识一次命令：相同 UUID 表示重试，复用完成结果或从检查点继续；同一个 UUID 如果对应不同简历则拒绝执行。简历内容哈希只用于业务复用：新 UUID 遇到未变化的简历会生成一条轻量使用记录并返回原画像、匹配卡和方案，随后扫描仍建立新的扫描轮次。只有用户明确传入 `--refresh-profile` 才对相同简历重新生成画像和方案。

后续扫描、补读和重评继续使用已有 CLI，并通过 `--agent` 选择当前外层 Agent。招聘网站安全边界不变：扫描只读；沟通、发送和投递仍需用户对具体批次明确授权。

## 前端边界

模型设置页只保留 API Key 配置。Agent 路径不启动 Dashboard，文档也不得要求 Agent 把用户带到网页完成设置。
