# OfferGo 用户旅程质量改造设计

**日期：** 2026-09-22  
**状态：** 已由用户确认  
**范围：** Windows 启动反馈、消息行动收件箱、求职体检、简历工作室与面试训练页面性能

## 目标

让普通用户从双击 OfferGo 到处理招聘消息、查看求职进展的全过程都能获得明确反馈，并消除需要用户理解内部术语、替系统补资料或进入招聘平台完成常见动作的产品缺口。

## 已确认的问题与证据

1. 桌面快捷方式直接启动隐藏 PowerShell。控制台仍可能短暂出现，随后在服务、专用 Edge 和平台工作区准备完成前没有可见反馈。
2. 求职体检页面只突出已联系、已回复和回复占比；现有漏斗数据已经包含已读、有效沟通、索要简历、面试邀请与面试确认，但没有完整呈现。
3. 智联结构化简历邀请已经支持同意或拒绝动作；BOSS 文本中的明确简历请求仍可能被当作普通消息生成回复草稿。
4. 消息草稿模型输入未携带平台和已识别的平台动作，因此会生成询问邮箱等脱离当前平台语境的表达。
5. 消息详情直接展示 `opportunitySummary`、`fitSummary` 等内部分析文字，并固定展示未知工作安排，造成“可迁移证据”“最高归入可投”“工作安排未确认”等用户无法使用的信息。
6. 当前验收数据下，本地实测 `/resume-optimization?planId=1` 约 5.65 秒，`/interview?planId=1` 约 3.77 秒；主要耗时来自每次页面打开重复启动 PowerShell 解密同一个 DPAPI 模型密钥，岗位数据读取约 82 毫秒。

## 产品设计

### Windows 启动反馈

安装包生成一个无控制台窗口的 `OfferGo.Launcher.exe`。桌面和开始菜单快捷方式直接启动该程序。

启动器显示当前小狗图标、持续旋转的进度环和一行状态文字。启动脚本通过仅包含固定枚举值的进度文件发布：

- `checking_install`：正在检查 OfferGo
- `starting_service`：正在启动本地服务
- `starting_browser`：正在准备专用 Edge
- `checking_workspace`：正在检查招聘平台
- `ready`：工作台已准备好

启动成功后关闭启动器。失败时保留窗口，显示公开错误信息和“打开诊断信息”按钮。启动器不保存用户数据、模型密钥或招聘平台内容。

### 消息动作与回复

消息处理分成两条互相独立的输出：

1. **平台动作**：发送简历、接受或拒绝平台卡片。
2. **文字回复**：回答沟通时间、到岗、项目经历等问题。

明确的简历请求首先生成 `send_resume` 动作。只有消息中还包含其他待回答事项时才生成文字草稿。发送简历与回复同时存在时，页面分别提供两个确认入口，不允许草稿代替平台动作。

任何外部动作都必须由用户在当前消息卡片上明确确认。同步消息本身保持只读。动作继续使用不可变目标、幂等键、单次点击、结果核验和不确定结果停止规则。

BOSS 简历发送能力只有在当前登录页面完成只读 DOM 校准、目标身份核验和结果标志确认后才启用。无法证明结果时不得重试。

### 平台语境草稿

草稿输入增加：

```js
{
  platform: "boss" | "zhaopin",
  requestedActions: ["send_resume"],
  messages: [{ messageKey, text }]
}
```

模型和本地合同共同执行以下规则：

- BOSS 消息默认在 BOSS 完成，智联消息默认在智联完成。
- HR 未明确提出邮箱、微信或电话时，不得主动建议切换渠道。
- `send_resume` 已由页面提供时，草稿不得承诺稍后发送、询问发送方式或声称已经发送。
- 只索要简历时草稿数组为空。
- 简历和其他问题同时存在时，草稿只回答剩余问题。

### 消息详情展示

详情区按用户任务排序：

1. `HR 希望你做什么`
2. 可执行按钮或需要补充的事实
3. `是否值得继续`及一条普通语言理由
4. 已知的岗位事实
5. 折叠的岗位分析依据

未知字段不渲染。页面不显示阶段名、模型档位、数据来源、可迁移证据、可投上限等内部术语。推荐理由根据结构化字段生成用户语言，不直接透传模型内部摘要。

### 求职体检

当前方案按平台展示：

- 已联系
- 已读或确认送达（平台支持时）
- 已回复
- 有效沟通
- 索要简历
- 面试邀请
- 面试已确认

同时展示等待反馈、状态未知和超过七天无进展的数量。漏斗比例只使用已知分母，不把未知状态当作失败。

增加三个用户可记录的最终结果：`interview_completed`、`offer_received`、`withdrawn`。拒绝和机会关闭沿用现有终止状态。页面先展示事实；只有样本达到既有成熟度规则时才显示诊断建议和平台、方向、简历版本对比。

### 页面性能

运行中的 Dashboard 缓存模型运行状态和模型适配器，以设置文件和密钥文件签名作为版本。读取页面只使用缓存的公开就绪状态，不重复启动 PowerShell 解密密钥。模型设置保存后立即失效缓存。

验收目标：当前验收数据下，简历工作室与面试训练的服务端响应时间分别低于 500 毫秒；更改模型设置后下一次模型操作使用新设置。

## 视觉方向

OfferGo 的主题是“可靠地陪用户把求职动作做完”。沿用现有黑白手绘小狗，不引入新的装饰性角色。

- 纸白 `#F7F7F4`：主背景
- 墨黑 `#20211F`：正文与关键动作
- 草绿 `#5D7C59`：成功与继续推进
- 琥珀 `#C4873A`：等待与需要确认
- 雾灰 `#E7E8E2`：边界与次要区域

启动器的唯一动态元素是围绕小狗图标的细线进度环。消息页的唯一强调结构是“行动条”，把动作放在详情最前面。求职体检使用横向阶段轨道表达真实顺序，不堆叠无意义的数字卡片。

## 验收边界

- 不改变 Dashboard 地址、CLI、Agent 协议和既有 SQLite 数据。
- 不在消息同步时执行发送简历或文字回复。
- 不为性能缓存写入明文密钥或日志。
- BOSS 与智联外部动作必须在真实登录 Edge 中验证目标和结果。
- 自动测试通过后，先由 Codex 在真实 Edge 走完整功能路径；用户最终只需要判断展示和使用体验。
