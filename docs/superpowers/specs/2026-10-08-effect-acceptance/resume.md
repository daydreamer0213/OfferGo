# OfferGo 简历优化：独立效果验收标准

制定日期：2026-10-08。范围：通用优化、针对明确岗位的专项优化、完整简历的编辑与导出。本文是待执行的效果标准，不是当前产品通过验收的结论。

本标准先于查看实现、模型输出及历史验收结果制定。只参考本轮用户要求、`docs/frontend-ux-principles.md` 的简历产品要求和下述高校职业中心原始指导；未读当前实现、未运行模型。所有案例均为合成审查素材，不代表真实候选人。

## 1. 用户真正应得到什么

候选人拿到一份能直接继续编辑、核对并导出的完整简历。招聘者能更快判断此人的教育和工作阶段、实际做过什么、贡献如何、技能用于哪里；针对岗位时，更容易看到与核心工作相关的真实经历。候选人能在面试中解释简历里的每一个事实。

成功不等于“改得多”“词更高级”“每句有数字”“关键词更多”或“内部评分更高”。不能以承诺获得面试、录用或业务增长作为本轮验收依据。证据只够支持“内容和交付更好”时，应如实止于这个结论。

`docs/frontend-ux-principles.md` 第 10 项规定：无岗位也能通用优化；明确岗位下突出相关经历；交付可编辑完整简历，不能只有修改建议；不编造成果、不丢原版本。本标准将其落实为成稿检查，而不按程序中有哪些字段组织标准。

## 2. 原始指导核实及中文求职边界

以下为少量原则摘要；后面的具体判定属于本轮用户要求和独立验收设计，不声称高校逐条规定了这些产品门槛。

| 一手来源（2026-10-08 核实） | 原文指导的实际支持 | 用于本标准的边界 |
| --- | --- | --- |
| [Harvard MCS：Creating a Strong Resume](https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/) | 简历应具体、基于事实、易浏览，突出能力；针对岗位反映雇主看重的技能，不要求所有经历直接相关；格式与时间顺序清楚；AI 可辅助编辑，简历须真实代表本人。 | 支持清晰、事实和相关性。学校同时提醒各国规范不同；其无照片、年龄等美式规则不直接成为中国求职硬门槛。 |

| [MIT CAPD：Crafting an effective resume](https://capd.mit.edu/resources/career-toolkit-crafting-an-effective-resume/) | 经历可包括实习、个人项目等；可用项目、行动、结果组织描述；无精确数字时仍可清楚描述个人角色和结果。 | 课程、未上线项目可凭真实交付与验证表现能力，不要求商业收入或真实用户增长。 |

中文适用性由本轮明确要求界定：保持专业术语、教育与工作阶段、真实项目属性和联系方式；中文叙述可自然省略主语，不照搬英文动词句式。不声称中国 HR 有统一几秒筛选规律，不把某套排版、照片、毕业院校顺序或英文 ATS（简历筛选系统）模板规定为全市场标准。岗位或用户明确要求优先；未知要求不自行补入。

## 3. 必须通过的底线

任何一项不通过，整体不得称为“优化成功”，其他表达提升不能抵消。

| 必须项 | 审查动作 | 通过表现 | 不通过表现 |
| --- | --- | --- | --- |
| 事实与身份准确 | 逐条对照原简历和本轮已确认补充材料，核查新增断言 | 公司、学校、专业、学历、日期、职位、阶段身份、技术、数量、成果都可追溯；实习仍是实习，课程仍是课程 | 虚构技术/数字；学生项目变上线商业项目；参与变主导；实习变正式任职；将进行中写成已完成 |
| 贡献归属准确 | 查“我做了什么”与“团队/公司做到什么”是否分开 | 在所属项目中说明本人的动作；团队成果保留团队或活动期间的限定 | 团队收入全部归个人；他人的架构设计变本人设计；支持执行升级为策略负责人 |
| 时间线与学历结构保留 | 按事件核对时间、状态及章节身份 | 教育信息可完整辨认；不同阶段日期一致；并行经历如实保留 | 为匹配把教育标题改为工作经历；抹平日期制造连续就业；改毕业时间；把在读写成已取得学历 |
| 项目之间不拼接冒认 | 将技术、动作、结果分别回溯到具体项目 | 可总结多段经历共同表现的能力，但每条具体成果仍属于原事件 | 将项目 A 的数据库、项目 B 的缓存和项目 C 的压测结果拼成 A 的完整交付；合并不同公司的成果 |
| 真实技能逻辑 | 同时查技能分类、掌握程度和经历支撑 | SQL 可列查询语言，Spring Boot 可列框架；“了解”不变“熟练”；重要技术及业务术语保留 | 把 Spring Boot 当语言、SQL 与 MySQL 混为一物；JWT 泛化成“安全能力”；单次接触升级为精通 |
| 核心资料与原版本保留 | 核对姓名、已有联系方式、学历、关键任职记录和原版可取回性 | 已有手机号/邮箱等正确保留；不丢关键教育信息；原版仍可查看/恢复 | 删除联系方式、生成假邮箱；丢学历；覆盖原版无法取回。原始资料本来缺联系方式时不得编造，成稿外提示缺口 |
| 完整交付 | 阅读编辑区全文，再下载导出文件检查 | 成稿含应有的全部部分，可编辑；用户修改可进入导出文件；文件可打开，中文、日期、顺序和关键内容正确 | 只交建议或修改片段；导出建议页；正文含“请补充”“此处填写”模板残片；导出旧稿、空稿或缺段 |

新增事实指的是原材料没有支持的事实主张；正常同义改写、拆句、合并同一事件的重复描述、调整标题/顺序不自动判错。原材料写“完成原型”可以润色为“交付原型”，但不能推断已上线、已取得用户验证或促成业务增长。模糊事实可以保守保留、成稿外提出针对性问题；不因缺少可选数字把整个简历退回半成品。

## 4. 应观察的效果

先判断原稿是否真的有问题，再比较前后。观察结果须引用具体前后句子/章节位置，不能只填“专业”“提升”“符合”或打分。

| 观察点 | 通用优化应产生的作用 | 专项额外应产生的作用 | 假改善或退步 |
| --- | --- | --- | --- |
| 结构和阅读路径 | 基本资料、教育、工作/实习/项目、技能可辨；同类内容一致，减少长段与重复；章节可按阶段重要性安排 | 与岗位相关的真实能力更容易被先看到，同时保持各章节时间线和身份清楚 | 给所有段落加“相关经历”；只换标题；为突出关键词把日期和归属打散 |
| 具体行动与重点 | 从流水账中显出对象、本人动作、方法或交付，去掉无信息形容词 | 优先展现承担核心工作所需的真实动作，而非照抄任职要求 | “负责相关工作”变“赋能业务”；每句硬填背景/任务/行动/结果使内容冗长 |
| 贡献与结果 | 已有成果说清范围和依据；没有业务结果时说明真实交付、修复、验证或阶段进展 | 成果/方法与目标工作的关系更明显，不擅自提升因果强度 | 未上线项目被迫加入增长率；把“用于评审”改“获得采纳”；把相关性改成因果性 |
| 专业准确、自然表达 | 技术名称和业务指标不损失含义，必要上下文说清；可读、没有空泛套话 | 保留岗位识别能力所需的正确专业词，并说明做过什么 | 为“普通人易懂”把事务、幂等、PRD、ROI 全删成“优化流程”；堆术语无动作 |
| 信息完整与篇幅取舍 | 保留关键教育、履历、联系渠道和有价值差异，删除重复及空话 | 减少无关内容的篇幅/优先级，但不损害身份、时间和重要能力证据 | 追求一页而删关键事实；把所有不直接匹配的经历删掉；凭空加个人总结 |
| 岗位真实相关性 | 无 JD 时不臆造具体岗位、目标公司或经验门槛 | 用完整 JD（岗位说明）识别核心工作、必要要求、加分项；有真实证据的核心能力得到具体强调 | 没有电商经验写“电商专家”；看到要求 Kubernetes 就加技能；只在开头附一段匹配结论 |

STAR（背景、任务、行动、结果）/PAR（项目、行动、结果）是组织经历的辅助思路。对关键经历可用其中合适元素帮助读者理解；基础技能清单、短职责、既已清楚的成果句不必凑四部分。不能以套用率、数字覆盖率或修改字数验收。

“专项有效”的最低证据：对该 JD 最重要、且候选人确有素材的能力，改后出现可指出的具体强调（如提前相关条目、补清原材料中的动作/方法、减去冗余），招聘者能指出对应项目或任职。若原稿已经清楚覆盖核心能力，维持即可；如果缺少核心能力，只能如实保留缺口，不能要求每项都补上。

## 5. 好坏对照和润色边界

下表的“好”以原素材具备对应事实为前提，不是可以无条件复制到任何人的通用句。

| 原材料 | 可以接受的润色 | 不接受的改法及理由 |
| --- | --- | --- |
| 做访谈并把反馈整理为需求表；完成原型用于课程展示 | 整理访谈反馈形成需求表，并完成供课程展示的交互原型 | “主导产品从 0 到 1 上线，推动用户增长”：改变身份、阶段及结果 |
| 参与订单接口开发，负责输入校验及异常响应 | 在订单接口开发中完成输入校验和异常响应处理 | “设计高并发订单架构”：参与范围没有支撑设计或高并发 |
| 学历：某大学，信息管理本科，2022.09—2026.06 | 教育经历：某大学｜信息管理｜本科｜2022.09—2026.06 | “产品相关工作经历：某大学”：教育被伪装成工作，标题匹配不是能力展示 |
| 在课程项目使用 Redis；另一个实习使用 MySQL | 分别写在对应项目下，技能栏可列 Redis、MySQL 并保持原熟练程度 | 将实习写成“基于 MySQL 和 Redis 设计缓存体系”：跨项目挪用技术 |
| 执行促销报名、与设计核对素材；期间店铺 GMV 增长是团队结果 | 执行促销报名并协同设计核对素材；活动期间店铺 GMV …（团队结果） | “主导增长战略，个人实现 GMV …”：执行变主导，团队变个人 |
| 原句已经准确简洁，重要信息清晰 | 原样保留，必要时统一标点即可 | 改成“赋能、全链路、闭环”等词并删具体对象：风格变化不等于进步 |

## 6. 三类候选人的前后比较审查卡

所有素材只能取自测试前固定的完整输入及已确认补充材料。以下数字是刻意放入的合成事实，用于检查是否保留、错误迁移或升级；不是模型可以补出的“推荐数字”。每个案例都必须使用完整简历，含虚构但固定的测试联系方式、完整教育记录与日期。案例卡只展示核心片段，不能据此允许输出片段稿。

### 卡 A：新毕业产品经理候选人，课程项目尚未上线

**固定事实。** 2022.09—2026.06 信息管理本科，已毕业；2025.10—2025.12 课程小组“校园活动报名”；本人参与需求整理，访谈 5 位同学、比较 3 个校园报名流程、整理需求表、绘制报名/取消流程及 Axure 原型，原型完成课程展示；没有线上用户、商业收入、A/B 实验、SQL 或实际产品经理工作经历。其他成员负责视觉设计和演示，本人不是组长。

**待改善原句。** “参加校园报名项目，做调研需求原型，和同学合作，完成课程。学习能力强，喜欢产品。”

**通用合格方向。** 保持“课程项目”及本人角色，将调研、需求梳理、流程/原型分成可读条目，例如“访谈 5 位同学并比较 3 个校园报名流程，整理需求表；绘制报名、取消流程及 Axure 原型，完成课程展示。”仍须保留教育、日期、技能和联系方式，空泛性格表述可减少。

**专项 JD。** 初级产品岗位的核心工作为需求调研、流程/原型、需求文档、协作沟通；加分项为数据查询和上线后指标分析。审查前固定 JD，不从输出倒推要求。

**专项应看见。** 调研、流程/原型更靠前且动作清楚；课程项目能作为能力证据。缺少 SQL 和上线后指标分析保持事实缺口，不能改为“熟悉数据驱动增长”。不要求虚构 PRD：只有需求表时就说需求表，不把其自动升级成完整 PRD（产品需求文档）。

**拒绝表现。** “主导需求”“产品已上线”“转化率提高 20%”“具备 SQL 数据分析”；因无增长结果删除整个课程项目；每句套 STAR 把短项目拉成模板叙事。

**比较记录。** 改前/改后读者各指出：学历与毕业状态、项目性质、本人的两项动作、实际交付、专项最相关证据、仍无证据的能力。结果是“更清楚 / 一样清楚 / 更难辨认”，附原句，不用“变专业”作唯一判据。

### 卡 B：初级后端候选人，三个项目证据不能混用

**固定事实。** 2021.09—2025.06 计算机本科；2025.07—2026.09 初级后端岗位。工作项目 A：Java、Spring Boot、MySQL，参与订单接口开发，本人完成参数校验、异常响应，补充接口文档，接口通过同事联调；没有吞吐/延迟数字。课程项目 B（2024.03—2024.06）：Python、SQLite，个人实现图书借还记录；课程练习 C（2024.09）：跟随教程使用 Redis 做缓存练习，未做生产部署。原技能程度：Java/Spring Boot/MySQL 用于工作，Python/SQLite 用于课程，Redis 了解。不得把 B/C 技术或个人归属迁到 A。

**待改善原句。** “用 Spring Boot 做订单后端，写了接口，校验错误文档联调。学习过 Redis。做过图书系统。”

**通用合格方向。** 工作 A 写清本人参数校验、异常响应、文档/联调，技术正确关联；B、C 各保留项目阶段。可将散乱技能分类、压缩重复，但不能把“了解 Redis”升为熟练。

**专项 JD。** 订单后端开发，要求 Java/Spring Boot、MySQL、接口可靠性、联调协作；缓存经验为加分项，分布式经验不是本素材已具备事实。

**专项应看见。** A 的接口开发、异常处理、文档/联调成为重点；Redis 若保留，应清楚为课程练习和了解程度；不必把它作为主卖点。不能凭空写“幂等机制”或“事务一致性”；若输入确有这些术语，应准确保留，不能统统简化成“处理问题”。

**拒绝表现。** “独立设计订单系统”“通过 Redis 将延迟降低 30%”“熟练 Python 后端生产开发”；将三项目合成一个“Java/Python/MySQL/Redis 高并发系统”；把无数字的真实交付判为没有成果。

**比较记录。** 改前/改后分别画出三个项目—本人动作—技术—结果归属，检查项目 A 是否更易辨认；列出所有新增能力断言的来源。专业表达变简洁但信息损失必须记为退步。

### 卡 C：有经验电商运营候选人，数字、口径及因果不能放大

**固定事实。** 2018.09—2022.06 市场营销本科；2022.07—2024.02 运营助理；2024.03—2026.09 电商运营。当前岗位本人负责每周汇总店铺漏斗数据，用 Excel 比较访客、加购、支付转化，并按商品整理问题清单；参与一次促销，负责平台报名和与设计核对素材，向负责人提交复盘。活动期与给定同长度对照期 GMV 分别为 123 万和 110 万，该店整体团队数据；促销有折扣及渠道投放，无证据证明某个动作单独造成增长。无团队管理、投放预算决策、SQL 或直播运营经历。

**待改善原句。** “店铺运营，报活动做表格，和设计对接，复盘活动。GMV 从 110 万到 123 万。熟悉电商。”

**通用合格方向。** 展现漏斗数据比较、问题清单、报名/素材协作和复盘；如保留 GMV 则明确“活动期店铺 GMV 123 万，对照期 110 万（团队结果）”，不声称个人因果。助理阶段不变成负责人阶段。

**专项 JD。** 店铺活动运营，核心为数据复盘、活动执行、商品表现分析、跨部门协作；预算投放策略/直播为加分项。专项突出原有分析动作，不把 Excel 写成 SQL，不为补加分项冒认投放负责人。

**专项应看见。** 数据分析与复盘动作优先、指标有口径和事件归属；协作执行可体现贡献，不以“主导增长”包装。若计算增长率，必须依据给定同口径数据正确计算、保持活动团队限定；直接保留两个数字同样合格，无需增加百分比。

**拒绝表现。** “ROI 提升 30%”“主导投放带来 GMV 增长”“管理跨部门团队”“拥有直播运营经验”；把 GMV（成交总额）换成利润/收入；删掉对照期或团队限定只保留大数字。

**比较记录。** 读者能否指出本人三项动作、指标比较的两个期间/口径、整体团队成果、职位阶段。对专项核心能力的阅读便利是否提高，而不是数字和“增长”出现次数提高。

## 7. 无须修改也是合格结果

将卡 C 的事实整理为一份已经清晰、无重复、日期/归属准确、已有联系方式及学历、且已突出专项核心能力的完整好简历，作为独立保留样本 C-good。它与卡 C 的粗糙版共享事实，但文本不同；在看输出前固定。

通用和专项都允许原样保留正文、统一少量格式或说明“现稿已清楚表达，无需内容改动”。仍需提供完整可编辑简历和可用导出，不得只输出“无须修改”一句。拒绝为了显示工作量重写、添加总结、替换为套话、增加数字或拆散结构。对本来好的句子，只要维持质量就通过，不要求制造提升。

## 8. 统一前后审查卡（每个结果独立填写）

### 输入与盲读

- 样本编号、候选人阶段、通用/专项、固定原简历版本、固定补充事实版本、专项完整 JD 版本、运行时间。
- 查看输出前列出原稿 0—3 个真实问题，以及“已有证据可支持”的专项核心能力；好稿写“无明显需改处”。
- 改前和改后先按随机 A/B 顺序阅读，不展示模型评分和修改建议。先记录可读性和相关性判断，再揭示哪个是新稿并核对事实。至少一位能按 HR/岗位阅读的人作内容评审，一位事实核对者查原材料；这两类判断均须记录，不能只由生成模型自评。
- 可使用固定 30 秒初读任务比较“能否找到身份、最近经历、个人贡献和岗位相关能力”；30 秒是本次统一测试条件，不是行业普遍规律。随后全文精读，不以初读替代真实性审查。

### 必填记录

| 项目 | 应填内容 |
| --- | --- |
| 原稿问题 | 具体原句/位置，或者原稿已合格的理由 |
| 改后重要变化 | 最多 3 个具体前后对照；未变化可记录保持 |
| 事实核对 | 所有新增/强化断言及来源；数字、因果、主导性、项目归属、日期身份、重要技能逐项核对 |
| 阅读与逻辑 | 更清楚 / 持平 / 退步，附可观察的句子、章节或查找结果 |
| 贡献展示 | 本人做什么、怎么做、交付/验证/结果是否更明确；缺少可选数字是否仍成稿 |
| 专项相关性 | JD 核心能力及其原始素材；改后具体强调在哪里；缺口是否仍真实；通用填不适用 |
| 不必要修改 | 原来正确的句子是否被改差；是否新增套话、术语丢失、重复或段落膨胀 |
| 完整可用性 | 联系/教育/履历完整；编辑一处真实文字、保存后返回并导出，确认导出包含修改；全文与文件检查结果；原版可取回 |
| 最终判定 | 改善通过 / 保持通过 / 不通过 / 未验证，并附主要理由及未验证范围 |

可辅助用 0—2 记录每一观察维度：0=明显退步或仍未解决原稿的关键问题；1=可用但问题仍有/与好稿持平；2=具体改善，或原本优良且完整保持。专项相关性在通用模式不计。不能把分数加总后抵消硬底线，不能预设必须每项满分或一定要有某个提升幅度。

**改善通过：** 底线全通过，原稿的主要问题得到至少一个实质解决，没有重要阅读/表达退步；专项再满足第 4 节的真实相关性要求。

**保持通过：** 原稿本来已清楚且适配，底线全通过，保持质量且完整交付；不以改动量扣分。

**不通过：** 任一底线失败，或原稿的主要问题只有标签/套话变化而没有实质改善，或有明显信息/逻辑损失。任何虚构能力、身份升级或跨项目冒认均应单独报告，不能藏在平均分里。

**未验证：** 未取得完整输入/完整文件或缺少必要观察；明确缺失范围，不把它算通过，也不把工具失败直接伪装成内容质量结论。

## 9. 最低有代表性的样本与执行方案

最低为 **4 份完整简历 × 两种模式 = 8 份结果**，使用 3 份固定完整 JD。此方案是首轮发现典型问题的最低覆盖，不是统计可靠性证明，也不代表所有职业/简历普遍通过。

| 固定完整简历 | 通用结果 | 专项结果 | 独立覆盖点 |
| --- | --- | --- | --- |
| A：新毕业 PM 粗糙稿 | A-general | A-job | 无工作经历、未上线、可选数字缺失、真实调研数字、课程身份、数据能力缺口 |
| B：初级后端粗糙稿 | B-general | B-job | 专业词准确、技能程度、无性能数字、三个项目的技术/贡献不能串用 |
| C：电商运营粗糙稿 | C-general | C-job | 多职位阶段、已有业务数字、指标口径、团队结果、协作与主导的边界 |
| C-good：同事实已清楚的好稿 | C-good-general | C-good-job | 不强制改写、保持专业词与结构、完整编辑/导出 |

1. 在见输出前固定并校验 4 份完整简历、3 份 JD、事实清单、预期重点和禁止新增项；文件版本/哈希归档。用虚构固定联系信息，不混入真实求职资料。
2. 针对同一粗糙稿分别做通用和专项，各模式一次，使用相同事实材料。专项必须有完整 JD，不能只给职位名；操作条件、模型标识、失败/重试情况留档，不能挑选多次运行中最好的一份而隐去其余结果。
3. 按第 8 节盲读后核事实；所有新增事实都查，不能只抽样查好看的三句话。通用和专项并排比较，检查是否真的围绕 JD 核心能力调整，以及缺口是否如实存在。
4. 每份结果检查完整文本和可打开的导出文件；至少每种模式实际做一次编辑—保存—离开/返回—导出—核对编辑内容。内容效果、编辑/导出链路分别报告；只验证接口文本不能宣称普通用户完整使用通过。
5. 汇总按“样本 × 模式”列判定与具体证据。出现真实性失败时直接作为关键失败报告；关键修改后重跑失败样本及相关通用/专项配对，不能沿用修改前分数。

若首轮全通过，可扩大到每类各一份已清楚好稿（共 6 份简历、12 份配对结果），再加入时间交叉、原始资料缺联系方式、核心岗位不匹配和更长履历。此扩展用于增加覆盖；最低 8 份结果未运行前，不凭案例模板声称效果已经得到验证。
