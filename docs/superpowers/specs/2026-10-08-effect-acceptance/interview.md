# OfferGo 模拟面试：独立效果验收标准

日期：2026-10-08。用途：在查看待验收输出之前，先确定什么样的题目、追问、反馈和重答才算有用。本文件是验收依据，不是当前产品的通过报告。

本次只根据用户目标、产品规范中的用户意图与公开权威资料建立标准；没有读取实际面试输出、旧审查结论或实现代码，没有调用模型。下述案例全部虚构，不是用户真实资料，不是任何公司的实际题库。字段名称、提示词格式、评分接口和页面布局不构成效果标准。

## 1. 验收要证明什么

用户应当能练习与自身经历和目标工作有关、实际面试官有理由提出的问题；回答后知道自己已经证明了什么能力、哪里还缺证据；在不虚构经历的前提下，把一次弱回答练成更切题、更具体、更可信的回答。

最终成功信号不是“生成了题目/评分/报告”，而是以下四件事同时成立：

1. **题目值得练。** 可以从真实简历或目标 JD（岗位职责与要求）说明为什么问、考查什么，以及难度为什么适合这个角色。
2. **对话像在了解能力。** 追问解决当前回答中的真实疑点；证据充分后转向下一项重要能力，不机械追问、重复问题或执着于数字。
3. **反馈能用于下一次回答。** 指出答案里具体的有效证据与缺口，给出可执行的改进动作；重答确实补齐原缺口才算进步。
4. **积累的资料真实且受用户控制。** 练习回答、假设方案和示范答案不会自动变成本人履历；用户能核对、修改、确认、撤回真实经历。

到岗时间、期望薪资、是否在职、住址、面试时间等日常登记信息，尤其已在 HR 沟通中确认的信息，不作为独立能力训练题。职业动机、转型理由、经历空档如何解释可以训练，但必须围绕职业判断、真实准备与岗位理解，不换一种说法重复登记。

## 3. 每一道题都要有可追溯的理由

验收者为每道主问题及实质追问写一张简短理由卡。理由卡是审查记录，不要求普通用户逐题阅读一大块内部说明。

| 理由卡项目 | 必须能回答的事 | 不合格例子 |
| --- | --- | --- |
| 输入依据 | 简历的哪段事实、JD 的哪项核心职责/要求，或回答中的哪句话；保留原文短句及位置 | 仅写“与岗位匹配”；把系统猜测当简历事实 |
| 考查能力 | 这道题主要区分哪项能力；能力能落实为行为、知识或判断 | “综合能力”“职业素养”而没有具体行为 |
| 问题 | 一道自然、清楚、有答题空间的问题；必要场景条件已给出 | 连问七件事；用内部标签和行业黑话包装空问题 |
| 为什么可能问 | 做这份工作为什么需要了解此能力；简历声明/转型缺口为什么值得核实 | “这题很常见”；“JD 有 Python，所以问所有 Python 八股” |
| 好答证据 | 哪些可观察证据能证明能力；哪些替代路径同样合理 | 只要求说出关键词、套模板或提供漂亮数字 |
| 难度与职责边界 | 应届/初级/有经验角色需做到什么；候选人参与与主导的区别 | 要初级候选人承诺全公司架构/预算结果；默认参与者就是负责人 |

**一题通过条件：** 六项均有实质内容，链条没有跳跃；主能力清楚，可以接受多种合理回答。问题不必照抄输入，但推导必须成立。针对基础知识的问题可以来自简历声明的技能或岗位入门要求，不要求所有基础题都绑到某次项目事故。

**追问的额外条件：** 能指出当前回答里的具体疑点，并说明追问后会多获得哪项判断依据。只能用候选人已经说过的事实；允许引入明确标注的假设变化，用来考查迁移判断，不得写成候选人已经经历过的事。

### 3.1 通用训练与岗位专项的区别

| 模式 | 出题依据与目标 | 通过信号 |
| --- | --- | --- |
| 通用训练 | 从本人真实简历中的重要项目、工作、学习、转型及其声称具备的基础能力出发；理解本人行动、知识、合作与复盘 | 换另一份经历明显不同的简历，题目的主要内容和评价证据随之变化；没有 JD 仍能训练 |
| 岗位专项 | 先识别指定 JD 的核心工作与入职要求，再用简历中的适配经历和真实缺口考查岗位准备度 | 同一简历换成职责不同的 JD，重要主题和难度发生合理变化；不混入另一公司的任务 |
| 指定薄弱点重练 | 保留原题意/能力及上次缺口，围绕它练一次更好回答或等价问题 | 能比较前后有效证据；不会无理由重启整轮或换成无关题 |

专项不应把 JD 的每个词都变成题。先判断什么是岗位核心工作，再选能区分准备程度的问题。简历缺失某项经历不等于必然不会：可以问基础理解、迁移经验或明确假设的工作情景；不能要求把从未做过的工作讲成成功故事。

## 4. 整轮覆盖与追问尺度

### 4.1 先列主题，再看整轮是否有意义

验收前从输入独立选出 3–5 个优先主题，写明优先理由。此数量是本次审查便于操作的参考，不是行业法定题数或产品硬编码。短训练可以只练其中一项，但应如实表示范围，不能宣称“全面检验了岗位胜任力”。

- 通用：至少有真实经历深挖和与本人背景相称的基础能力；学习、协作、动机可按经历价值选取，不能固定每人同样五题。
- 专项：核心职责应得到实质考查；简历里最重要的相关经历应被利用；有价值的关键缺口应被探查。若一轮太短，保留未练主题供后续，不把“尚未考查”写成“不具备”。
- 一道题可以反映多项能力，但应有主要目标，避免凭一次答案给所有能力贴标签。
- 同一经历可用于不同能力，但必须有不同考查点；换措辞继续要求同样背景、行动、结果，不算新增覆盖。
- 各主题的重要性和评价尺度在回答前确定。候选人话多、术语多或数字大，不应使系统临时更换评分标准。

### 4.2 何时追问，何时换主题

| 当前回答情况 | 合理动作 | 失败表现 |
| --- | --- | --- |
| 只有“我们做了”，个人职责不清 | 问本人负责哪一步、做了什么决定 | 直接评价“领导力强”；要求承担团队全部成果 |
| 做法具体，但依据/取舍不清 | 针对其做法问为什么选它、替代方案或约束 | 换成另一个无关模板题 |
| 声称结果很好，但结果口径不明 | 问如何判断、观察到什么、是否有记录；允许非数字证据 | 逼给百分比；指导“编一个可信的数字” |
| 技术结论存在实质漏洞 | 针对漏洞追问边界、失败情形或验证方法 | 仅因为关键词齐全给高评价 |
| 回答离题或问题没理解 | 温和指出偏离处，重述核心问题，给一次聚焦机会 | 把篇幅增加当进步；不断扩大问题 |
| 用户明确没有该经历/不知道 | 区分经验缺口与知识缺口；可换成相关真实经历或明确假设的方案题 | 不相信“没做过”，反复追问“当时你怎么实现的” |
| 所需证据已充分 | 简短承接，转向尚未覆盖的重要主题 | 不断“还有呢”；反复要结果/数字 |
| 回答产生可信的新疑点 | 允许针对该疑点追加一次实质追问 | 仅为凑题数继续深挖 |

普通主题建议主问后 0–2 次聚焦追问；超过两次时，验收记录需说明仍有哪些重要、可回答的疑点。此尺度是检查“是否没完没了”的产品参考，不能机械禁止复杂技术/案例题中的自然澄清。连续两次没有新增证据时，应考虑换问法或转题，而不是一直要求同一答案。

一次追问尽量解决一个主要缺口。允许候选人先问清目标、约束和术语；在信息不足的情景题中主动澄清本身可能是好证据。系统不得故意隐瞒必需条件，再因未猜中隐含设定扣分。

**整轮通过条件：** 优先主题覆盖与实际训练时长相称；追问有新增判断价值；转题有合理时机；未覆盖主题和证据不足均如实记录。题数达标不是充分条件。

## 5. 逐答反馈、复盘、重答与确认资料

### 5.1 每次反馈应回答四件事

1. **本题实际考查什么。** 用普通话说清能力，不显示一串内部标签。
2. **这次答出了什么。** 引用或准确概括答案中的具体内容，说明它证明了哪一点；不能把未提到的能力或结果补出来。
3. **还缺什么，为什么影响判断。** 例如“说了团队做了筛选，但还不知道你如何确定优先级”；区分“答案没有展示”与“本人没有能力”。
4. **下一次做什么。** 给一至两个最重要的具体改法，可用一个聚焦问题帮助回忆真实经历。允许提供结构和表述示例，但未知事实用待填写项，不能替本人写结论。

技术题应检查方法是否正确、适用条件、主要边界与验证方式；不能只看 STAR 或表达是否流畅。动机题应看对目标工作的理解、真实转型准备、选择逻辑与限制，不要求编一个“从小热爱”的故事。情景题应看澄清、判断顺序、取舍与验证；不把假设方案当既往业绩。

反馈以本题真正需要的能力证据为准。内部资料保留个人与团队的准确事实，对外回答优先展示本人的行动、判断、方法和交付。普通经历、方法或学习问题不要求主动附上“同事负责”“团队成果”“不能归因”等声明；缺少这些字样不构成缺口，添加这些字样也不自动提高评价。直接问独立负责、协作或如何验证成果时，才按问题检查相应职责、分工或验证限制是否说清；技术方案的适用条件仍按技术正确性检查。任何问题都不能冒认职责、虚构结果或夸大因果。

### 5.2 能力证据的统一判断尺度

以下是对答案的人工检查等级，不是必须展示给用户的分数，也不是录用标准。对不同角色先写各题自己的证据锚点，再按此检查。

| 等级 | 含义 | 例子 |
| --- | --- | --- |
| 未展示 | 离题、仅自我评价或复述题意，无法判断本题能力 | “我执行力很强”“我们效果很好” |
| 部分展示 | 有相关真实内容，但关键行动、依据、边界或验证缺一项，不能充分判断 | 说做了访谈，没说如何处理冲突需求 |
| 达到角色所需 | 关键证据清楚，做法/理由合理，职责和不确定性真实，能应对该角色的典型任务 | 初级后端说明可行做法并知道主要失败边界 |
| 更充分 | 在同样真实前提下，能解释重要取舍、约束、局限或迁移；不要求大项目/大数字 | 解释为何方案只适用于当前条件，并说明进一步验证 |

“不知道”“没有做过”可以是诚实的有效边界，但不能自动等于掌握该能力。结果不佳也不自动是差回答：如果判断、行动、复盘清楚，可以展示成熟的学习与诊断能力。

### 5.3 这些情况不能算重答进步

- 更长、语气更自信、增加“赋能/闭环/抓手”等术语，却仍未回答本题。
- 添上 STAR 标题或“我主导”，但个人行动与职责仍不清。
- 新增没有来源的百分比、预算、用户规模、管理经验，或者把“会这样做”改成“当时这样做了”。
- 复制系统示范里的虚构故事；数字或技术结论矛盾没有解释。
- 修好了一个表达问题，却破坏原来正确的技术判断或真实事实。

**真进步：** 在不增添虚构事实的条件下，补上上一答缺少的相关个人行动、决策依据、验证、边界或结论；或删去干扰并更明确地回答核心问题。没有新事实时，通过组织已有内容变得更切题也可以进步。

这里的“边界”必须影响本题判断。例如成果验证题补充可比条件有价值；代码评审题只在末尾添“发布由同事负责”，没有新增修正方法、测试或学习，不能单凭这句算进步。

重答反馈必须对照“原缺口→新答案中的实际变化→还剩什么”，不能仅说分数提高。若补充的真实经历与简历不一致，应让用户解释/修订，不直接认定欺骗，也不自动抹平矛盾。

### 5.4 整轮复盘要能指导下一次训练

复盘应给出：本轮练了哪些主题；每项能力已有证据及出处；一至三个最值得改善的缺口；对每个缺口明确下一次练哪类题、补充什么真实信息或复习什么基础知识。没有考到的能力标为未考查，避免“全能/不适合岗位”等过度结论。

不能将某一道题的低评价扩大成候选人的人格判断；不能把练习结果包装成企业录用概率。分数可辅助浏览，但不代替具体帮助。

### 5.5 确认资料必须产生真实、可控的效果

| 操作/资料 | 应发生的效果 | 不通过条件 |
| --- | --- | --- |
| 原始练习回答 | 用于当轮训练与复盘；未经确认，不进入后续简历/消息作为个人事实 | 一次假设回答就成为“本人经验” |
| 提出可保存经历 | 展示来自哪道题、哪段用户原话；总结不扩大职责、数字、结论 | 把示范答案、模型追问或推断作为用户原话 |
| 用户修改后确认 | 保存用户核对后的真实表述；后续相关内容可复用，同时保持原职责和事实边界 | 保存仍是确认前版本；“参与”被扩成“主导” |
| 适用范围 | 通用经历可用于相关场景；具体公司承诺只适用于相应范围；动态事实需考虑时间 | 把旧岗位薪资承诺、旧到岗日期当当前通用事实 |
| 不确认/撤回 | 后续新内容不把它当有效个人资料；历史练习仍可作为当时记录查看 | 撤回后新答案继续沿用，或旧内容偷偷恢复 |
| 重复确认、切页、回来查看 | 不制造相互矛盾的重复经历；用户能看见有效版本及确认状态 | 重复操作产生多个不同事实，状态不明 |

复用成功不是简单“出现某字符串”：新输出应在相关场景正确使用已确认经历，不能在无关问题硬塞故事；应通过完整句意、职责边界、适用范围来判断。

## 6. 三组虚拟案例：题型、好坏对照与难度

以下简历、JD、回答均为验收构造。参考好答展示证据形态，允许其他合理答案，不可作为用户可直接粘贴的真实经历。

### 案例 A：新毕业生申请初级产品经理

**虚拟简历 A：** 信息管理本科应届生；做过校园预约小程序课程项目，负责访谈、需求整理和交互原型，后端由同学实现；访谈 6 名同学；原型做过两次同学走查；无商业上线结果；曾协调开发同学处理范围争议；会基础 SQL。

**虚拟 JD A：** 初级 PM 在资深同事指导下做用户需求分析、需求文档、研发沟通与功能验收，协助分析功能使用情况；不要求独立负责业务营收或成熟增长实验。

**本轮优先主题：** 把需求变成可验证问题；有限资源下的优先级；与研发合作；基础数据判断。校内经历是合适证据，不能因没有商业 ROI（投入产出）压低其回答。

#### A1 通用经历/行为题

- **输入→能力：** 简历“负责访谈、需求整理和原型”，考查能否从真实反馈辨别用户问题、说明本人贡献。
- **问题：** “校园预约小程序里，讲一个你从同学反馈中发现并处理的具体问题。你做了什么，怎么判断改动有帮助？”
- **为什么可能问：** 简历声称做过需求分析；面试官有理由了解它是照搬需求还是基于观察做判断。
- **好答证据/难度：** 具体反馈；本人整理与判断；原型变化；走查观察及局限。应届角色不要求商业增长证明。
- **弱答：** “我们做了问卷和用户调研，产品很受欢迎，我沟通能力强。”
- **较好答：** “两位受访同学说找不到可预约时段。我把访谈里这类反馈单独归类，检查原型后发现入口只显示日期，时间藏在下一页。我把可用时段移到日期旁。第二次走查时同学能找到入口，但样本少，而且没有正式上线，不能说提高了预约率。”
- **合理追问：** 弱答问“选一个反馈，你本人做了哪一步”；较好答若无新疑点，应换主题。不能强逼“提高了多少百分比”。
- **反馈方向：** 弱答缺具体行动与判断依据；建议用一个真实反馈说清修改和走查观察，而非编用户满意度。

#### A2 岗位专项工作情景题

- **输入→能力：** JD“需求分析、研发沟通、验收”，简历尚无商业上线，考查有限范围的优先级判断与验收意识。
- **问题：** “假设预约功能只能再开发两天，用户希望加提醒，开发认为先修取消预约后名额未释放的问题。你会怎么确定先做什么？”
- **为什么可能问：** 是该角色会参与的需求取舍；既能利用原型经验，也不假定其管理完整团队。
- **好答证据/难度：** 澄清影响和复现情况；优先处理核心流程缺陷；与资深 PM/研发确认；给出可检查的验收条件。合理不同选择需有清楚条件。
- **弱答：** “用户第一，都做，加班解决。”
- **较好答：** “我先确认名额问题是不是稳定复现、影响哪些预约。若取消后一直占名额，核心流程已受影响，会建议先修并与负责人确认，再把提醒记入后续。验收至少检查取消后名额释放、重复取消不会多释放名额；提醒可先说明暂不支持。”
- **合理追问：** 若其只说优先修 bug，问“你会怎样验收”；不能升级成制定全公司季度路线图。
- **反馈方向：** 判断不是看喊“用户第一”，而是看是否识别核心风险、约束、协作和验证。

#### A3 动机与准备题

- **输入→能力：** 应届身份、课程项目经历及 JD 的初级 PM 工作，考查目标理解与真实准备。
- **问题：** “你为什么选择初级产品经理？校园项目中哪部分工作让你形成这个选择，你还需要补哪些能力？”
- **为什么可能问：** 工作选择与对岗位内容的理解影响初级角色的准备度；不是重新登记求职状态。
- **好答证据/难度：** 连接真实经历与需求/协作工作；说出吸引点和不喜欢/需补部分；说明已经做或计划做的具体准备。
- **弱答：** “产品经理发展好，我天生善于沟通，能负责增长。”
- **较好答：** “访谈里的模糊抱怨变成原型修改这一步我最感兴趣，但我还不熟悉上线后的数据分析。我投初级岗位，希望在指导下把需求到验收做扎实；已经在用课程项目的数据练基础 SQL，不把这说成增长经验。”
- **合理追问：** 问具体 SQL 练习或怎样理解日常工作；不问“既然想做 PM，预期薪资是多少”当能力训练。

### 案例 B：初级 Java 后端开发

**虚拟简历 B：** 1 年 Java 后端经历；参与 Spring Boot 订单接口，负责参数校验、状态变更和部分单元测试；用过 MySQL，处理过一处列表慢查询；生产发布由资深同事负责；没有独立设计支付系统或百万并发系统的经历。

**虚拟 JD B：** 开发订单 REST API、处理 MySQL 查询与事务、协助排查接口问题、写自动化测试和代码评审；初级岗位，遇到复杂故障需在指导下处理。

**本轮优先主题：** 订单状态/并发正确性；数据库基础；问题定位与验证；本人负责范围。不能因简历写了 Spring Boot 就一直背注解，也不能要求独立主持跨地域容灾。

#### B1 通用技术经历深挖

- **输入→能力：** 简历“处理一处列表慢查询”，考查基础诊断与验证方法。
- **问题：** “讲讲那次列表慢查询：你怎样确定慢在数据库，做了什么修改，又怎样检查是否有效？”
- **为什么可能问：** 核实简历所称优化的技术理解与本人行动，符合初级职责。
- **好答证据/难度：** 具体查询/过滤条件；排查证据；解释计划或其他合理诊断；改法与对比条件；数据量/环境局限。无需夸大性能成果。
- **弱答：** “加索引就快了，MySQL 索引越多越好。”
- **较好答：** “日志显示这条查询耗时较多，我先在测试库复现。它按用户和状态筛选并排序，我看执行计划后与同事讨论了联合索引。用同样数据和查询条件比较，再检查写入影响。测试数据量小，我没有把测试改善直接说成线上降了多少。”
- **合理追问：** 询问实际过滤/排序和为什么选该索引；答案若只是背索引定义，要回到实际查询。无法讲出真实细节时记录未充分展示，不替他补查询。
- **反馈方向：** 技术正确性与验证是重点；STAR 形式完整不能抵消“索引越多越好”的错误。

#### B2 专项技术与工作情景题

- **输入→能力：** JD“订单接口、事务与测试”，简历“状态变更”，考查并发请求下的状态正确性。
- **问题：** “假设同一订单因网络重试收到两次取消请求，接口怎样避免重复释放库存？先说明你需要知道的系统条件。”
- **为什么可能问：** 与实际核心职责相连，并能判断初级候选人的事务、条件更新和重试边界理解；不是要求其有支付系统经历。
- **好答证据/难度：** 澄清数据是否同库、订单状态和库存规则；可用条件更新或其他正确控制；把状态变更和同库库存操作置于一致性边界；只有成功转状态才释放；覆盖重试/并发测试。可接受其他合理方案。
- **弱答：** “前端禁用按钮，后端加 synchronized，就不会重复。”
- **较好答：** “我先确认是否多实例、订单和库存是否同库。如果同库，取消时可以用待处理状态作为更新条件，成功改变一次状态后再释放库存，相关操作在事务里；第二次请求发现已取消就返回已有结果。会测并发两次和中途失败。跨服务库存不能仅靠这个本地事务解决，我会和资深同事确认方案。”
- **合理追问：** 弱答问“如果两台服务实例同时处理呢”；较好答可核实事务边界，证据足够后转题。不能因没答分布式协议细节否定初级水平。
- **反馈方向：** 指出进程内锁对多实例不足；引导补系统条件、状态判断和测试，不让候选人编“线上零超卖”。

#### B3 行为/学习题

- **输入→能力：** 参与开发且由资深同事发布，考查接收评审、修正问题及协作边界。
- **问题：** “说一次代码评审发现你遗漏的问题。你如何理解建议、修改并防止再次发生？”
- **为什么可能问：** JD 要求代码评审和测试，初级成长能力有直接工作价值。
- **好答证据/难度：** 一个实际遗漏；本人如何核实与修正；补测试/检查方式；结果与学习。允许小缺陷，不要求重大线上事故。
- **弱答：** “我从不出错，同事都认可我。”
- **较好答：** “一次状态接口只检查了参数格式，没有检查当前订单状态。评审指出后，我按允许的状态转换补了判断和测试，并请同事看异常返回是否一致。后来相似接口我先列状态转换表。”
- **合理追问：** 问一个实际测试或状态转换例子；不把未负责发布写成“独立保障上线”。
- **自然表达对照：** 本题未问发布分工，较好答无需追加发布声明。只说“上线由同事负责，所以这是团队成果”而不讲遗漏和修正，仍未展示学习方法；若追问“你独立负责发布吗”，应答“我负责接口修改和测试，生产发布由资深同事负责”。

### 案例 C：有经验的电商运营，转向利润导向岗位

**虚拟简历 C：** 4 年平台电商运营，主要负责活动报名、店铺页面和商品转化分析；与投放同事、客服和供应链协作；做过一次活动前商品页改版；看过曝光、点击、下单、退款数据；投放预算由负责人批准，广告操作由投放同事执行；没有独立管理完整利润核算的经历。

**虚拟 JD C：** 负责店铺活动、商品转化优化、协同投放与库存、复盘销售和毛利表现；要求基于数据判断问题，不只追求 GMV（销售额）；角色需独立管理日常运营，但不等于财务负责人或投放专家。

**本轮优先主题：** 数据诊断；毛利与退款的取舍；跨团队协调；由转化经验向利润责任迁移的真实准备。比应届角色需要更多独立判断和验证，仍不扩大预算权限。

#### C1 通用真实经历/数据诊断题

- **输入→能力：** 简历“活动前商品页改版、分析转化”，考查诊断依据与贡献边界。
- **问题：** “那次商品页改版，你为什么认为页面是问题，改了什么，怎样判断变化与改版有关？”
- **为什么可能问：** 简历声称改善转化，有理由核实是否有分析、验证及谨慎归因。
- **好答证据/难度：** 数据口径与漏斗位置；客服反馈/页面观察；具体个人动作；同期变化与归因局限；非数字证据也可用。角色应能独立解释判断。
- **弱答：** “我改了详情页，GMV 翻倍，所以页面优化很成功。”
- **较好答：** “我看到商品访问到下单这一段偏低，客服也反复收到尺寸问题，所以我先把尺寸说明和退换规则移到前面。活动后下单改善，客服同类咨询也减少了，这些观察与改版方向一致。同时流量和价格也有变化，要进一步确认页面的作用，需要可比流量或更小范围测试。”
- **合理追问：** 核实可比较时间段/流量变化；没准确数字时可问观察或报告口径，不要求回忆编造精确百分比。
- **反馈方向：** 本题直接问怎样验证，评估具体观察、同期变化和后续验证是否支持结论；无需固定“不能归因”措辞或附投放分工。只说“都是团队成果，不能归因于我”而不给判断方法仍不足；说“改版单独造成全部增长”仍是夸大。

#### C2 岗位专项经营情景题

- **输入→能力：** JD“复盘销售与毛利、协同库存”，简历利润核算缺口，考查经营诊断和工作优先级。
- **问题：** “假设活动销售额增加，但毛利减少、退款也上升。你接手复盘会先查什么，再如何决定下一步？”
- **为什么可能问：** 新岗位不能只以销售额评价活动；场景直接对应核心工作，考查真实缺口的准备程度。
- **好答证据/难度：** 澄清毛利口径、时间和退款归属；按商品/渠道/优惠拆解；查折扣成本、商品组合、退款原因等合理假设；优先处理已确认风险；与财务/供应链对齐；明确验证和权限边界。不要求猜中唯一原因。
- **弱答：** “继续加投放，把销售额做大，毛利自然回来。”
- **较好答：** “先确认毛利是否包含优惠和相关成本，退款按哪一段时间算，再按商品和渠道拆开看。若增长集中在深折扣低毛利商品，先核对活动机制；退款集中在缺货或描述不符时，先与供应链/客服核实并调整相关商品。原因未确认前不扩大投放。预算变更需负责人同意，后续用可比周期检查毛利和退款有没有改善。”
- **合理追问：** 选一个其提出的假设，问需要什么证据/怎样排除另一个原因；不给条件却要求准确算出利润不合理。
- **反馈方向：** 好答在诊断、取舍和验证；列很多指标却没顺序、没有决策路径只算部分展示。

#### C3 转型动机与缺口题

- **输入→能力：** 简历侧重转化，新 JD 加强毛利责任，考查可迁移经验与真实补足计划。
- **问题：** “这份岗位更强调毛利，你过去主要做转化。哪些经验能直接用，哪些还需要补？你如何准备承担这部分工作？”
- **为什么可能问：** 工作责任变化值得核实；不是询问离职时间或重复薪资登记。
- **好答证据/难度：** 具体可迁移行动；承认核算/成本经验不足；已做准备与入职初期验证方案；不夸大预算或财务责任。
- **弱答：** “运营都一样，我以前已全面负责利润。”
- **较好答：** “按商品找转化问题、和客服供应链核实原因可以迁移，但我没有独立做完整利润核算。准备时我在梳理优惠、退款和成本口径，会先与财务对齐，再把利润维度加入日常复盘。我能独立推进店铺分析，但预算和财务口径仍需相应负责人确认。”
- **合理追问：** 核实已做准备的一项具体内容；不要求把准备计划改写成已经完成的经营业绩。

## 7. 固定对照：弱答应改好，离题长答应被识别

使用同一道题、同一候选人资料和同一评价锚点，按顺序输入以下版本。它们用于检查评价行为，不用于证明真实候选人的能力。

| 对照组 | 第一答 | 第二答 | 预期反馈与比较 |
| --- | --- | --- | --- |
| A1 弱答→真实补足 | “我们做了调研，效果不错” | A1 较好答 | 指明新增了具体问题、本人动作、走查观察及局限；可判进步；不因无商业指标否定 |
| A1 弱答→长但离题 | “我们做了调研，效果不错” | 长篇介绍产品经理职责、学校荣誉和“用户第一”，仍没有一个真实反馈与本人动作 | 仍未展示本题能力；不能因长度/结构完整判进步；指出核心缺口依旧 |
| B2 错误→补足边界 | 前端禁用按钮/进程内锁 | B2 较好答 | 识别修正了多实例与状态控制问题，评价关键边界；不把诚实承认跨服务局限当退步 |
| B2 错误→术语堆积 | 前端禁用按钮/进程内锁 | 加上微服务、DDD、分布式、高可用等词，仍未解释谁只释放一次库存 | 技术缺口未修正；不能因技术词变多提高能力判断 |
| B3 方法完整→追加无关分工 | B3 较好答 | 同一答仅追加“发布由同事负责，这是团队成果” | 方法和学习证据未增加，不因此加分；原答不因未写声明扣分 |
| C1 夸大→谨慎归因 | “GMV 翻倍都是我改页的结果” | C1 较好答 | 肯定区分同期变化与归因；新增可靠判断可以算进步，即使数字变少 |
| C1 无数字→捏造数字 | 不记得准确值，只描述观察 | 声称“转化提高 37%、ROI 提高 52%”，输入与回答此前均无此记录，并表示是为好看编的 | 不接受为有效改进；建议删除或核实；不能保存为真实经历 |
| C3 真实缺口→假经历 | 承认未独立核算利润 | 复制示范，自称做过全年利润预算 | 不算进步；指出与资料/原答矛盾，要求核对，不能静默确认 |

补充反例：用户明确说“没做过 A/B 测试”，系统仍问“当时怎么划实验组”；用户已说明“由同学实现后端”，系统仍评价其“全栈开发能力强”；用户解释“只有测试库对比”，系统生成“线上响应时间降低”。任何一个出现都违反证据边界。

## 8. 可直接执行的验收方案

此方案不要求新增依赖、验证器或数据库框架。按当前可用界面/命令执行，人工保存输入、完整对话与操作结果即可。不得用格式合规、关键词命中、离线假返回替代内容评价。本文件准备阶段不执行模型，后续由获授权的验收者实施。

### 8.1 先准备，后看输出

1. 固定产品版本、模型名称/版本、实际设置、日期、候选人输入版本和 JD 全文；使用隔离的虚拟候选人资料，避免污染真实用户经历。
2. 使用上述三组资料；每组先写一页独立预期：3–5 个优先主题、可接受难度、关键经历边界、最重要缺口。不要根据生成题目反向改预期。
3. 准备第 7 节的好坏回答，以及每组一份“已确认 HR 登记资料”：例如到岗、薪资、在职状态已确认。这样能检验系统会不会拿现成登记字段凑训练题。
4. 对每组分别做通用训练和岗位专项训练，保留完整原始题目、答案、追问、反馈和复盘，不只保存摘要。

### 8.2 最小验收批次

| 检验 | 执行方式 | 必须看到的成功信号 |
| --- | --- | --- |
| 三类背景×两种模式 | A/B/C 各做通用、专项，共 6 轮；完整轮以覆盖预期优先主题为结束依据，短轮另记录 | 通用利用真实简历；专项落实 JD；难度角色相称；无日常登记题凑数 |
| 追问与转题 | 各轮交替给部分答、充分答、明确没做过；观察下一题 | 部分答有针对性澄清；充分答能转题；没有经历时不制造过去事实 |
| 同题重答 | 三组各至少做一次弱→好、一次弱→长离题，保留前后反馈 | 真实补足才算进步；长离题没有得到更高能力评价 |
| 技术正确性 | 使用 B2 正误对照，审查状态、事务、实例边界与验证 | 能指出关键技术问题；不只奖励词汇/STAR |
| JD 改变 | 同简历 C，把 JD 改为内容/直播运营（核心为内容策划、直播流程、内容转化），保持其他资料 | 专项转向内容准备、相关可迁移经验与缺口；不继续以毛利题占满核心主题 |
| 简历改变 | 同 JD A，将简历替换为只有社团活动与调研课程、没有预约项目的毕业生 | 不再问不存在的预约项目；可用真实社团/课程经历及工作情景 |
| 缺失 JD | 通用无 JD；专项缺少核心职责 | 通用可进行；专项如实说明资料缺口/尝试获取必要资料，不捏造公司的核心工作 |
| 确认资料 | 某轮补一条真实经历；先不确认，再编辑确认，再撤回，分别生成相关新内容 | 未确认不当事实；确认采用编辑后的准确内容；撤回后新内容不再使用 |
| 资料边界 | 尝试保存假设方案和示范答案；用另一候选人/无关岗位新生成 | 不误认本人经历，不混用候选人，不扩大岗位范围 |

6 轮只是最低跨背景样本，不是充分统计评估。完成一次没有失败，不能声称所有简历都可靠。若要宣称稳定，至少对六种组合各增加一次独立生成，并重复失败相关对照；每轮保留原始结果，不选最好样例、不以重试覆盖首轮失败。重复次数和通过范围应在报告中明确。

### 8.3 每个问题的人工记录

至少保留下列信息，可以用普通 Markdown 表格或现有表格软件：

- 输入版本、模式、题号/回答位置、完整问题、对应回答与反馈。
- 第 3 节六项理由卡；主问/追问/转题；追问前实际缺什么、追问后新增什么。
- 内容判断：通过/部分通过/不通过/未验证；一句具体理由和原文证据。
- 重答：原缺口、新证据、真实性与技术正确性、进步或未进步的理由。
- 复盘：主题覆盖；证据出处；未考查项；改进动作是否能够实施。
- 确认资料：原话、拟保存内容、用户编辑后内容、确认/撤回动作及后续使用结果。

验收者先独立按理由和证据判断，再查看系统分数，避免被高分引导。技术题需要具备该技术基础的审查者；运营/产品题对有争议的方案，应记录条件和可接受的替代答案，不用个人偏好当唯一答案。若两位审查者判断不同，围绕具体锚点与原答核对；不能简单平均分数抹掉事实矛盾。

## 9. 通过门槛与失败处理

### 9.1 不可用其他高分抵消的失败

下列情况只要在验收批次出现一次，对应能力/链路即不通过，不能被平均分或其他好样例抵消：

- 编造/扩大候选人经历、个人职责、数字、结果；诱导为了得高分补假经历；假设方案或示范答案成为真实资料。
- 日常登记信息成为独立能力训练主问；已确认的 HR 条件被重复训练并当成核心覆盖。
- 专项主要问题与实际 JD 核心工作脱节，或明显把别的岗位任务、别的候选人资料带进来。
- 对同题长离题/术语堆积答案判明显进步，未指出仍缺核心证据；关键技术错误被流畅表达掩盖。
- 用户明确没做过仍被要求讲“当时”，或证据充分后持续重复追问同一缺口而不换主题。
- 未确认/已撤回的资料进入后续新内容，确认后使用的却是错误版本。

### 9.2 可修正但不能忽略的问题

问题措辞略绕、反馈改法不够聚焦、复盘略重复，可记为部分通过；必须指出具体影响并修正后验证。若妨碍用户回答或重练，则升为不通过。不能用“语义大致正确”放过缺少证据的空反馈。

**该批次通过需同时满足：** 每道主问的理由链成立；追问有回答依据与价值；预定主要主题得到相称考查；三类对照均能区分真进步与伪进步；反馈/复盘可操作；确认资料链路正确；无上述不可抵消失败。部分通过项尚未修正时，不宣布完整效果通过。

任何失败应按“用户目标→实际输出/操作→原文证据→影响→最小改法→复验结果”记录。复验先重复原失败输入和同题对照，再检查邻近的另一背景/模式，确认没有只修一个案例。已经执行的失败样例保留，不替换成新的成功样例。

## 10. 报告应如何下结论

报告至少交代：实际完成哪些场景/轮次；哪些判断有原始输入与完整输出支持；发生多少失败；哪些是资料不全或尚未验证；修后是否重做原对照。

允许的结论示例：“A/B/C 三种虚拟背景的通用与专项训练共 6 轮，在本批次能按真实经历/JD 出题，识别长离题答案，并在确认后准确复用经历；技术深度只覆盖初级订单场景，其他岗位和长期稳定性未验证。”

不允许的结论示例：“面试模块全面通过”“真实 HR 一定会问这些题”“所有候选人能力都能准确评分”“提高 20 分证明面试成功率提高”。

本文件只建立上述标准及检验方法，不证明当前 OfferGo 已符合其中任何一项。
