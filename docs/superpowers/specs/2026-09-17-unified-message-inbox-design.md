# OfferGo 统一消息收件箱设计

## 目标

将现有“消息发现与回复”改造成统一消息收件箱。用户打开页面后无需选择任务类型或平台，系统自动告诉用户：发生了什么、是否需要现在处理、下一步做什么。

本设计同时解决四个已确认的问题：

1. 读取前没有刷新消息页，可能使用旧状态。
2. 项目首次使用时不能证明覆盖最近 72 小时的既有会话。
3. 一条岗位资料读取失败会停止整个平台的剩余消息。
4. 页面把分类工作交给用户，并展示了用户不需要理解的读取状态和内部错误。

消息读取、岗位补全、分析和草稿生成仍为只读准备行为。发送消息、发送简历和投递继续要求用户针对具体内容明确确认。

## 已验证的当前行为

2026-09-17 使用现有验收环境进行只读检查后确认：

- BOSS 消息列表当前能提供稳定的 `lastTS` 和 `updateTime`，可以确定最后活动时间。
- 智联消息列表当前能提供 `sendTime`，其值与列表显示的最后活动日期一致。
- 当前读取器只读取已经加载的列表行，扫描前仅恢复后台页面生命周期，没有重新加载页面。
- 当前智联列表加载了 20 条会话，其中 18 条因末条消息来自对方而进入队列，包含数月前的历史会话。
- 智联队列第一条发生岗位详情身份不一致后，整个平台停止，后续会话没有继续处理。
- 当前持久化数据中的智联未解决记录，其岗位编号确实存在于智联消息页；没有发现 BOSS 卡片与智联卡片在数据库中交叉绑定。现有标签表达不够清楚，用户无法直观看出它表示的是“消息渠道”。

这些事实表明，问题不只是页面文案，而是同步范围、失败隔离、持久状态和页面信息层级共同造成的。

## 产品语义

### 首次衔接

每个候选人、每个平台独立记录消息同步状态。没有成功同步记录时，视为首次衔接。

首次衔接必须纳入：

- 最后活动时间位于读取开始时间前 72 小时以内的全部会话，不区分最后一条消息由谁发送。
- 当前仍为未读的全部会话，即使最后活动时间早于 72 小时。
- 以前已被 OfferGo 记录为未解决、但尚未处理完成的会话。

因此，用户在使用 OfferGo 前主动联系的岗位也会进入收件箱。尚未收到回复的会话显示为“等待对方回复”；收到回复的会话进入“现在需要你处理”或其他自动分类。

### 后续同步

后续每次读取都先刷新平台消息页，再从上次成功同步点继续。系统同时检查当前未读消息和持久化的未解决项目，避免只依赖时间游标而漏掉状态变化。

同步完成后保存平台、覆盖起点、完成时间和最新活动时间。同步未完成时保留已经写入的安全检查点，但不能把覆盖状态标记为完整。

### 覆盖证明

平台消息通常按最后活动时间倒序排列。读取器必须验证列表时间单调不增，并持续加载较早会话，直到满足以下任一条件：

- 已读到早于 72 小时边界的会话，可以证明最近 72 小时已覆盖。
- 平台明确显示没有更多会话。
- 出现登录、风控、页面丢失或列表结构变化，无法继续安全读取。

如果列表没有覆盖到 72 小时边界，系统保存部分结果并明确显示“本次只更新了部分消息，可稍后继续”，不能宣称已经完成最近三天同步。

为了避免无限滚动，读取保持串行、受现有访问节奏和预算约束，并通过检查点分次完成。质量目标不因单次安全上限而降低。

## 同步流程

### 1. 后台刷新

消息控制器绑定当前固定的 BOSS 和智联消息标签页。每个平台开始读取前：

1. 重新解析当前标签页 ID、窗口 ID、URL 和前台状态。
2. 在不切换前台标签页的情况下执行页面重新加载。
3. 等待目标 URL、登录状态、页面结构和消息列表恢复就绪。
4. 再次验证标签页 ID、窗口 ID 和前台状态没有变化。

刷新失败时不删除上次结果。页面显示上次成功更新时间，并说明本次没有获取到最新状态。

### 2. 列表采集

BOSS 行增加经过校验的最后活动时间、岗位标题和公司字段；智联行增加经过校验的 `sendTime`。时间必须是合理范围内的 Unix 毫秒值，异常值不能参与覆盖判断。

读取器只返回结构化会话摘要，不执行岗位分析或草稿生成。摘要包含：

- 平台和会话键。
- 平台岗位编号。
- 最后一条可靠消息编号。
- 最后活动时间。
- 最后消息方向和已读/送达状态。
- 未读状态。
- 岗位标题、公司和最新消息摘要。

### 3. 持久化统一收件箱

新增一张轻量的会话状态表，按“候选人 + 平台 + 会话键”唯一。它保存当前收件箱所需的最新状态，不保存完整聊天副本：

- 平台、会话键和平台岗位编号。
- 可选的本地岗位、进度卡关联。
- 最后消息编号、时间、方向、读取状态和摘要。
- 岗位标题、公司。
- 自动分类、用户可见行动说明和当前处理状态。
- 首次发现、最后同步和最近成功处理时间。

完整的已读取入站消息继续使用现有 `message_inbound_contexts`，草稿继续使用现有草稿表，未解决信息在迁移期继续兼容现有 `message_discovery_unresolved_items`。不建立完整聊天归档，也不引入通用消息总线。

另增加每个候选人、每个平台一条同步状态，用于记录 72 小时覆盖和增量同步水位。

### 4. 岗位上下文补全

需要用户处理的既有会话，如果没有本地岗位资料，消息流程自行完成：

1. 使用消息页提供的平台岗位编号核对当前会话。
2. 复用完整且属于当前候选人、当前方案和同一平台的本地岗位分析。
3. 本地没有完整资料时，使用现有后台临时详情页安全读取 JD。
4. 保存岗位、建立进度卡并执行消息所需的岗位分析。
5. 生成分类结果和回复草稿。

用户不需要先到“今日任务”发现岗位，也不需要手工选择关联岗位。只有平台无法提供可靠岗位身份、岗位已下线且资料不足，或出现多个无法自动区分的本地候选时，才进入“系统暂时无法完成”。

### 5. 失败隔离

以下错误只影响当前会话，记录原因后继续下一条：

- 岗位详情与会话标题或公司不一致。
- 岗位已下线或 JD 不完整。
- 单条消息内容类型暂不支持。
- 无法为单条会话建立完整岗位上下文。
- 单条模型分析失败或草稿校验失败。

以下错误停止当前平台，因为继续读取不能证明安全：

- 登录失效或出现风控验证。
- 固定标签页丢失、切换窗口或身份绑定变化。
- 消息列表结构无法识别。
- 浏览器连接中断，无法确认临时详情页是否已经关闭。

一个平台停止不抹掉另一个平台已经完成的结果。BOSS 与智联继续串行执行。

## 来源一致性

页面上的平台徽标统一表示“这条消息来自哪个平台”，文案写成“消息来自 BOSS”或“消息来自智联”。平台值必须来自对应读取器，不能根据岗位标题、公司或本地匹配结果推断。

建立或绑定岗位时必须同时满足：

- 会话平台与平台岗位编号前缀一致。
- 进度卡来源与岗位来源一致。
- 消息上下文来源与进度卡来源一致。

任一条件不满足时不得生成可发送草稿，项目进入单条“来源需要核对”状态并继续处理其他会话。

## 页面设计：行动收件箱

删除“要处理什么”和“消息来源”两个选择框。页面自动组合 BOSS 与智联结果，并按行动优先级分组。

### 分组

1. **现在需要你处理**
   - 新回复。
   - 面试邀请。
   - 索要简历。
   - 需要补充信息或确认关键事实。

2. **等待对方回复**
   - 用户最近主动联系，尚未收到回复。
   - BOSS 已读或已送达，当前无需操作。
   - 智联已发起沟通但平台没有提供可靠已读状态。

3. **系统暂时无法完成**
   - 岗位已下线或资料不足。
   - 会话和岗位身份不一致。
   - 消息内容暂不支持。
   - 本次只完成部分同步。

4. **已经处理**
   - 已确认处理或已关闭的联系，默认折叠。

组内排序以行动紧急程度优先，再按最后活动时间倒序。单条异常不会排在正常待处理消息之前。

### 列表行信息

每条列表只展示：

- 岗位名称和公司。
- “BOSS”或“智联”消息渠道徽标。
- 最后活动时间。
- HR 最新一句话；等待状态显示“你的消息已送达，等待 HR 回复”。
- 一句当前行动，例如“确认面试时间”“确认是否发送简历”“当前无需处理”。

列表不展示扫描队列长度、可见会话数量、内部阶段名称和错误代码。

### 详情信息层级

用户点开一条消息后，按以下顺序展示：

1. 岗位、公司、消息渠道、最后活动时间和当前行动。
2. HR 最新原话。
3. OfferGo 的简短判断：消息类型、岗位是否值得继续、回复前需要确认什么。
4. 可编辑的建议回复。
5. 与平台能力一致的操作：BOSS 可以进入明确确认后的发送流程；智联提供复制并返回原会话处理。

以下内容默认折叠：

- 为什么建议继续沟通。
- 完整消息记录。
- 岗位详情和完整分析。
- 其他回复版本。

内部读取详情、访问预算、错误代码和结构诊断只出现在诊断页及脱敏日志中。

### 用户可见错误

用户文案描述结果和下一步，不暴露实现：

- “岗位已下线，无法补全资料。请到智联原会话查看。”
- “这条会话与岗位资料不一致，OfferGo 没有生成草稿。请到 BOSS 原会话核对。”
- “本次只更新了部分消息，已经读取的结果可以正常使用。稍后可继续读取。”

不再显示 `MESSAGE_DISCOVERY_JOB_CONTEXT_UNAVAILABLE`，也不再要求用户先运行“今日任务”。

## 幂等与并发

- 同一平台、会话键和最后消息编号重复同步只更新观察时间，不重复生成进度事件或草稿。
- 同一会话的新消息使用新消息编号和消息组键更新原收件箱记录。
- 正在运行的读取拒绝重复启动，页面复用已有任务状态。
- 失败后的继续读取从平台同步检查点和单条会话状态恢复。
- 页面刷新不改变发送授权；已有发送批次运行时仍锁定对应草稿。

## 兼容与迁移

- 现有未解决项目、消息上下文、草稿和进度卡全部保留。
- 首次打开新版本时，页面先投影现有数据；完成第一次平台同步后补全统一会话状态。
- 不改变 BOSS、智联的固定标签页和后台临时详情页安全边界。
- 不改变现有消息发送授权边界。
- 不引入新的运行依赖、前端框架或通用仓储层。

## 测试与验收

### 自动检查

- 两个平台都在扫描前刷新，且不改变前台标签页、窗口和固定标签页身份。
- 刷新失败时保留旧结果并标明更新时间，不把旧结果描述为最新。
- 首次同步包含最近 72 小时全部会话和所有未读会话。
- 列表不足以证明 72 小时覆盖时继续加载并保存检查点。
- 后续同步只处理变化项，重复运行不重复创建事件、卡片或草稿。
- 最近主动联系但尚无回复的岗位进入“等待对方回复”。
- 项目使用前产生的新回复可以自动补岗位资料、分析并生成草稿。
- 单条详情身份不一致时继续下一条。
- 登录、风控、页面丢失或浏览器断开时停止对应平台。
- BOSS 与智联来源不允许交叉绑定。
- 页面没有任务或来源筛选框，四个自动分组顺序稳定。
- 列表和详情不显示内部错误代码。

### 人工验收

人工验收从桌面 OfferGo 快捷方式进入软件完成，不要求普通用户运行批处理文件：

1. 打开消息页，确认页面不要求选择任务类型或平台。
2. 点击“刷新并读取新消息”，确认两个平台在后台刷新且前台页面不被抢走。
3. 确认最近三天既有会话出现在正确分组。
4. 打开一条项目使用前产生的回复，确认能看到 HR 原话、岗位判断和草稿。
5. 制造或使用一条岗位资料无法补全的记录，确认它进入“系统暂时无法完成”，其他消息继续处理。
6. 重复点击读取，确认不会排队重复任务或产生重复草稿。
7. 核对每条记录的消息渠道、时间和行动说明。

人工验收不发送真实消息、不发送简历、不投递岗位。

## 实施顺序

1. 增加会话状态和同步状态存储，兼容投影现有数据。
2. 为两个读取器增加后台刷新、活动时间和 72 小时覆盖读取。
3. 将岗位上下文失败划分为单条错误和平台级错误，确保单条失败后继续。
4. 收口既有会话自动补岗位资料与分析的流程。
5. 用行动收件箱替换现有筛选页面，并保留草稿和发送边界。
6. 完成离线门禁后冻结精确提交，再生成最新点击式人工验收环境。
