# OfferGo 统一消息中心设计

## 目标

OfferGo 成为 BOSS 直聘和智联招聘的统一消息工作台。用户在 OfferGo 中查看有求职价值的消息、理解岗位、编辑回复并确认操作；除平台强制登录或安全验证外，不需要再打开招聘平台消息页处理业务。

本轮覆盖：

- 普通文字消息。
- 平台通知中会影响求职进展的内容。
- 请求发送简历、面试邀请、联系方式交换等操作卡片。
- BOSS 和智联的文字回复及已确认的卡片操作。
- 首次同步最近三天，后续增量同步。

本轮不处理语音、图片和附件。发现这些内容时保留消息类型和时间，不分析内容，也不因此阻断同一会话内其他文字消息。

## 已确认的问题

### BOSS 安全验证误报

当前消息控制器只要发现任一 BOSS 地址包含 `_security_check` 参数，就把整个 BOSS 会话判定为安全验证。2026-09-18 的真实页面检查显示：当前地址仍含该参数，但页面已登录、职位结构完整，页面内容没有安全验证信号。

安全状态必须由当前页面内容、页面路径和登录状态共同判断。`_security_check` 参数只能作为诊断信息，不能单独阻止读取。若同一浏览器会话中确实存在可见的验证页、异常页或登录页，仍立即停止 BOSS 操作。

### 消息类型覆盖不足

智联真实会话已经出现 `303`、`346` 和简历请求卡片等类型，现有读取器只接受普通文字和少数卡片，因此把可见内容降级为“无法读取”。BOSS 对语音、图片、附件和未知卡片也会把整组新消息判为不可处理。

读取器需要逐条保存已识别消息。一个暂不处理的媒体消息不能导致同组文字或操作卡片丢失。

### 消息展示依赖岗位详情

现有流程先尝试关联完整岗位资料，失败后把消息交给用户去平台处理。消息事实和岗位事实应当分开：消息读取成功后立即保存和展示；岗位详情只影响岗位理解、匹配结论和草稿质量。

### 智联没有回复写回

智联真实消息页已经提供文字输入、发送、发送简历、交换微信以及简历请求的同意和拒绝控件，但 OfferGo 的发送控制器只创建 BOSS 读取器和发送器，页面也只允许 BOSS 草稿进入发送批次。

## 方案选择

不继续用“增加一个错误码或卡片选择器”的方式修补现有摘要流程，也不镜像整个第三方页面。采用模块化单体内的统一消息账本：保留 SQLite、本地 Dashboard、现有浏览器适配器和串行执行器，增加一份完整、可增量更新的本地消息时间线。

该方案比逐项补丁多一个持久化步骤，但能够解决完整展示、断点恢复、幂等写回和跨平台一致体验。它不引入服务拆分、消息队列、ORM、前端框架或通用自动化框架。

## 数据设计

### 会话索引

继续使用 `message_inbox_items` 作为每个会话的索引，保存平台、会话标识、岗位关联、最后活动时间、未读状态和当前行动分组。

岗位关联允许为空。缺少岗位详情时，会话仍可进入收件箱。

### 消息时间线

新增 `message_events`，每条平台消息只保存一次：

- `profile_id`、`platform`、`conversation_key`。
- 平台消息标识或稳定摘要标识。
- 方向：招聘方、本人、平台。
- 类型：文字、平台通知、简历请求、面试邀请、联系方式交换、媒体占位、未知卡片。
- 可展示文字、发生时间和安全裁剪后的结构元数据。
- 首次和最后观察时间。

唯一键使用“候选人 + 平台 + 会话 + 平台消息标识”。平台没有可靠消息标识时，使用已规范化内容、方向、类型和时间生成稳定摘要。重复同步只更新观察时间，不新增重复消息。

媒体消息只保存类型和占位说明，不保存或下载媒体内容。

### 写回记录

文字回复继续复用现有草稿、批次和发送项目表，在发送项目中明确平台，由控制器选择 BOSS 或智联发送器。

非文字卡片操作使用独立的小型操作记录，保存：会话、源消息、动作类型、不可变输入摘要、状态、点击次数和结果证据。一次确认只允许一次平台点击；结果不确定时停止，不自动重试。

## 同步流程

1. 用户点击“同步最新消息”。
2. OfferGo 刷新两个平台的固定消息页，确认登录和页面真实状态。
3. 两个平台严格串行执行；同一时刻只读取一个会话。
4. 首次使用向前读取到最近三天的边界；后续从本地水位继续增量同步。
5. 每个会话先保存完整的受支持消息，再更新会话索引。
6. 岗位关联和详情补充作为后续步骤执行。失败只降低岗位理解和草稿质量，不删除消息，不阻止用户查看会话。
7. 新的招聘方文字或操作卡片进入“现在需要你处理”；最后一条是本人回复的会话进入“等待对方回复”；已经完成的进入“已处理”。
8. 同步因进程退出、暂停或平台短暂不稳定中断时，从会话和消息水位继续，不重读已完成会话，不重复创建草稿。

消息页切换继续使用随机非零间隔并严格串行。岗位详情读取继续使用原有更谨慎的访问预算和冷却，不因消息同步提速而放宽。

## 消息理解

平台读取器先把真实页面内容规范化为共同消息结构，应用层再决定展示和行动分组。

第一版必须识别当前真实样本中的：

- 普通招聘方和本人文字。
- 智联 `303` 富文本、`346` 平台提示和简历请求卡片。
- BOSS 普通文字、简历请求和已有平台通知。
- 从文字或已验证卡片中得到的面试邀请、联系方式交换和补充信息请求。

未知卡片不能清空同一会话的已读文字。系统保存其结构签名用于适配，并把该平台同步标为“不完整”，但不生成“请去平台自行查看这条消息”的用户任务。发布验收要求当前真实样本中的有价值文字和操作卡片全部归一化，未知项只能是本轮明确排除的媒体内容或无求职行动价值的展示项。

## 岗位资料降级

会话页始终先展示真实消息时间线。岗位资料分为三个状态：

- 完整：显示岗位理解、匹配判断和基于岗位的回复建议。
- 补充中：显示已知岗位名称、公司和消息，后台继续补充详情。
- 不可取得：显示消息和保守回复建议，并明确哪些岗位判断暂时无法完成。

岗位资料缺失不能再产生“请到智联或 BOSS 原始会话处理”的提示。草稿只使用已经证实的简历事实、消息原文和已取得的岗位事实，不猜测缺失信息。

## 平台写回

### 文字回复

BOSS 和智联共用现有的“保存草稿、用户确认、串行发送、结果核验、完成后学习修改”流程。平台发送器各自负责：

1. 重新核对会话和最后一条招聘方消息。
2. 填入用户确认的文字。
3. 在本地持久化点击所有权。
4. 点击一次发送。
5. 通过页面和网络结果确认平台已接受，并确认新发消息出现在正确会话。

会话变化、目标变化或结果不确定时停止后续项目，不自动补点。

### 操作卡片

只为真实页面中已验证存在的动作提供按钮，例如“同意发送简历”“拒绝”“确认面试信息”。每种动作必须有独立的目标核对和结果核验，不能用文字按钮名称猜测后直接点击。

用户在 OfferGo 中确认具体动作即授权该次不可变操作；历史确认不能重放，也不能授权其他会话。

### 平台强制步骤

真实登录失效或安全验证是唯一需要离开 OfferGo 业务页面的例外。OfferGo 显示平台连接状态并引导完成登录或验证；验证完成后，用户回到 OfferGo 重试同步，不需要再进入平台消息页处理会话。

## 页面设计

保持“行动收件箱”布局，但右侧改成完整会话：

- 左侧按“现在需要你处理”“等待对方回复”“系统正在补充资料”“已处理”分组。
- 每条会话显示平台、岗位、公司、最后活动时间和一句最新消息摘要。
- 右侧按时间展示完整文字消息和平台操作卡片。
- 岗位理解放在可折叠区，不占据消息主流程。
- 底部固定回复编辑区和当前会话可执行的操作按钮。
- 同步状态只描述平台级连接、覆盖范围和进度，不把解析失败包装成用户业务任务。

不再出现“请自行到 BOSS/智联原始会话查看或处理”的产品路径。

## 错误和恢复

- 地址中残留 `_security_check`：记录诊断信息，读取真实页面状态；页面健康则继续。
- 真实安全验证或登录失效：停止对应平台，另一平台继续，保留全部检查点。
- 单个会话结构暂时未加载：有限等待后保留水位，稍后重试，其他会话继续。
- 未知非媒体卡片：保存结构签名并标记平台同步不完整，不丢弃同会话已识别消息。
- 岗位详情失败：保留消息并降级岗位分析。
- 模型失败：保留消息，允许用户直接回复或稍后重新生成草稿。
- 发送前失败：不点击平台，可安全重试。
- 点击后结果不确定：标记结果待核对并停止批次，不自动重放。

## 迁移和兼容

- 现有 `message_inbox_items`、未解决记录、草稿和发送历史全部保留。
- 新表通过有序 SQLite 迁移创建，迁移前沿用现有备份机制。
- 旧的未解决项目在首次新同步时重新读取；成功写入时间线后自动消除，不要求用户手工清理。
- Dashboard 地址和启动方式保持不变。
- 现有 BOSS 发送数据继续有效；增加平台字段时使用岗位来源回填并验证一致性。

## 交付顺序

为避免一次改动覆盖过多外部页面行为，按以下顺序独立验收：

1. 修复 BOSS 安全验证误报，建立完整消息时间线和三天同步水位。
2. 补齐当前真实样本中的 BOSS、智联文字和操作卡片读取，移除岗位详情对消息展示的阻塞。
3. 在现有发送批次上增加智联文字回复，完成两端相同的确认、幂等和结果核验。
4. 增加已观察到的简历请求等卡片操作，完成统一页面和最终真实 Edge 验收。

每一步都保留前一步的可运行状态，并在提交前运行相关快速检查和完整离线门禁。外部写入验收必须单独取得对应测试会话和具体动作的授权。

## 验收标准

### 自动检查

- BOSS 地址含 `_security_check`、但真实页面健康时不会误报风险控制。
- 真实风险页仍立即停止 BOSS，智联继续。
- 首次三天同步和后续增量同步不会重复消息。
- 智联 `303`、`346`、简历请求以及 BOSS 当前受支持类型均能进入时间线。
- 媒体占位不阻断同会话文字。
- 岗位详情失败时消息仍展示、仍可编辑保守回复。
- BOSS、智联文字发送均执行目标核对、一次点击和结果核验。
- 操作卡片重复确认不会重复执行。
- 中断恢复不会重复创建消息、草稿、批次或平台动作。

### 真实 Edge 验收

从最终安装包启动并使用用户当前登录的 Edge：

1. 实际点击“同步最新消息”。
2. 验证 BOSS 和智联都完成最近三天或当前可达边界的串行同步。
3. 抽查两端会话的列表、完整时间线、岗位关联和草稿一致。
4. 验证岗位详情读取失败不会阻止消息展示。
5. 使用已明确授权的测试会话分别验证一次 BOSS 和智联文字写回；没有授权时只验收到发送确认前。
6. 使用已明确授权的测试卡片验证对应动作；没有授权时只验证目标核对和确认页面。
7. 重新同步，确认已发送内容和行动状态已回写且没有重复。

最终交给用户验收前，Codex 必须先完成上述真实路径中所有不需要外部写入授权的步骤。用户验收只判断页面展示、文案和操作体验；平台登录或真实安全验证除外。
